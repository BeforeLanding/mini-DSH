## 1. 结论与完成度

**运行时首阶段闭环基本完成；面向 coding agent 的仓库感知、可靠编辑和验证交付仍需补齐。** 下一阶段先让现有底座支撑可验收的代码修改任务，再用编程评测衡量上下文与预算策略的效果。

完成度应分层判断，不能把通过测试的比例当作产品完成度：

- **上下文容量治理：首版已实现。** 能估算包含 system、reasoning、工具 schema 的输入，按完整 task 裁剪旧历史，保护当前 task 所有 run，保证工具协议配对，容量不足明确停止。
- **执行预算治理：首版已实现，仍需边界加固。** 模型次数、工具次数、主动时间、累计 token、输出限额与独立超时已联动，配置快照、优先级、零额度与取消均有测试。本次发现裁剪和输出分配的衔接、最终持久化计时还有缺口。
- **持久化与续跑：有可演示的完整链路。** JSONL、单写入者锁、写入确认、恢复、unknown/skipped 和同 task 新 run 已落地。恢复后观测状态仍有遗漏；恢复不是任意执行位置的精确恢复，也不承诺外部副作用 exactly-once。
- **上下文质量管理：处于基础阶段。** 当前解决“请求装不装得下”，尚未验证“删掉什么以后任务仍能完成”。当前 task 无法压缩、大文件工具返回缺少分页、旧约束可能随历史一起移除，均限制长任务。
- **效果证据：尚未完成。** 没有真实模型任务集、完成率/用量对照或估算误差分布；57 条测试证明已覆盖场景的行为，不能证明实际任务质量或成本收益。
- **编程工作流：基础工具具备，专门契约不足。** 文件工具和 Bash 已可完成读改运行；默认身份仍是 general-purpose agent，环境上下文尚未自动组织仓库规则与项目检查入口。`edit_file` 已拒绝歧义替换和审批期间文件变化，但缺少任务级变更清单与 diff 交付。Bash 主要返回文本，缺少统一的结构化验证记录。
- **完成判定：目前是 run 结束语义。** Loop 收到无工具调用的完整回答即可记 completed，这不等于代码通过验收。后续应保留运行终态，同时增加独立的编程验证状态和证据，不能把所有问答强制变成测试任务。
- **求职展示：已有素材，尚需组织。** 最有价值的是事件事实来源与请求投影分离、预算检查与结算、失败恢复语义，而不只是“接了模型和 MCP”。需要把这些内容串成一次演示和一个可量化改进故事。

## 2. 值得保留和讲清楚的设计

### 原始历史与模型工作集分离

[SessionRuntime](../src/core/session-runtime.ts) 保存事件，[ContextBudgetRuntime](../src/core/context-runtime.ts) 派生请求。裁剪不删除原始事件；取消、跳过和恢复仍能追溯。这是目前最清楚的架构亮点。

按任务分组比“只保留最近 N 条消息”可靠，因为后一种方式可能拆开 tool call/result。代价是完整当前任务越来越大时只能停止。这是明确取舍，并非所有长上下文问题都已经解决。

### 预算覆盖调度与结算

[AgentLoopRuntime](../src/core/agent-loop-runtime.ts)、[RunBudgetRuntime](../src/core/run-budget-runtime.ts) 在调度前检查，响应后按 usage 结算；失败请求也计数，缺失 usage 标为 estimated/uncertain。实际 token 超估算时停止后续调度，而不是宣称绝不超费。

审批等待暂停主动时间、审批另有超时、非协作工具标 unknown，这些都能用来说明为什么 `maxSteps` 或一个 `Promise.race` 不足以管理完整执行生命周期。

### 恢复优先避免重复副作用

[JsonlStore](../src/core/event-store.ts) 和 Session 恢复保留“未执行”与“执行结果未知”的区别。`/continue` 是基于现有结果重新规划，不重放已经完成的工具；unknown 则阻止自动续跑。

这是比泛泛描述“支持断点续传”更准确的项目表述。测试中真实 Cordis、Bash、文件和恢复链路的组合，比全 mock 的简单单元测试更有说服力。

## 3. 本次确认的三个边界缺口

三个问题都在模拟模型、内存存储和可控时钟下复现；没有执行真实副作用。诊断脚本为 [review-probes.mjs](context-budget/review-probes.mjs)：

```powershell
pnpm build
node docs/context-budget/review-probes.mjs
```

脚本输出实际观察值，不是验证修复成功的测试，也没有加入 CI。后续应将期望行为写成正式回归测试；脚本输出随实现变化而变化。

### F1：输出额度收缩前已经裁剪历史（P2，优先修复）

位置：`AgentLoopRuntime.run()` 先用 `policy.maxOutputTokens` 调用 `project()`，再调用 `outputAllowance()`；`ContextBudgetRuntime.project()` 因此使用配置最大输出做裁剪预留。

复现：完整历史输入估算 754 token，总预算 854，最低输出 1、最大输出 1000，窗口 2902，安全余量 2048。保留完整历史时，实际可分配输出 100，恰好满足 `754 + 100 + 2048 = 2902`。

实际却先按 1000 输出预留移除旧 task，最后只发 1 条当前用户消息，输出额度为 544。没有超出容量，但丢掉了本可保留的上下文。现有测试分别验证了裁剪和额度收缩，没有覆盖两者交叉。

建议：在每个候选上下文集合上共同计算输入估算、剩余 token、实际输出额度和容量，再决定是否移除下一个完整旧任务。明确“历史保留与输出长度”的策略优先级，避免隐式取舍；仅当候选方案确实不可行时裁剪。

验收：上述样例保留旧任务并发送 100 输出额度；再覆盖余额不足最低输出、窗口等号/差一、旧任务被移除后重新计算、system/schema 不可裁剪及多个限制同时命中。

### F2：最终落盘等待超时后仍报告完成（P2，优先定稿终态语义）

位置：`AgentLoopRuntime.run()` 成功路径先采样 `activeDurationMs`、追加 completed 终态，再直接等待 `sessions.flush()`。该等待没有受 control 包装，返回前也没有复查。错误路径的最终 flush 同样没有等待上界。

复现：主动预算 10ms；模拟模型立即完成；内存存储在持久化 `run/finish` 时推进时钟 20ms。`agent.send()` 返回 `done`，状态仍为 completed，记录主动时间为 0ms，实际虚拟时间已经达到 20ms。

这与 R-05“主动时间包含持久化”和 R-08 终态可解释性的承诺存在偏差。源代码还存在最终 flush 永不返回时持续等待的路径，但本次未进行真实磁盘挂起实验。

建议：先定稿“任务执行完成”和“终态提交完成”的边界。对普通持久化等待使用明确 deadline；最终提交单独定义有界收尾和提交不确定状态。不要简单 race 后遗弃写入，或因迟到超时追加第二个相冲突的终态。相应更新 R-05、D-05 和事件契约。

验收：模型完成但最终 sync 跨 deadline、sync 挂起、取消与 sync 完成竞态、sync 失败四种情况均有可解释返回；唯一终态不冲突、写入未确认时不启动新 run、恢复结果与持久化事实一致。

### F3：崩溃恢复遗漏上下文投影信息（P2，观测一致性）

位置：`SessionRuntime.latestRun()` 在没有 `run/finish` 时只从 `model/start`、`tool/start`、`model/usage` 重建计数，未归并 `context/projection`。`restore()` 随后把这个不完整 state 封存为 error。

复现：日志已有输入估算 1234 和被裁剪任务 `synthetic-old-task` 的投影事件，但在终态前中断；恢复后原始事件仍在，run 的 `removedTaskIds` 却为空，`estimatedInputTokens` 缺失。

因此数据没有从原日志丢失，但 `/budget` 无法准确解释中断前的上下文变化。已有恢复测试主要检查工具状态、usage 和消息，没有检查投影字段。

建议：重放时合并同 run 的裁剪任务集合，并还原最近一次输入估算；区分请求尝试的投影与实际已发送请求。对崩溃时无法精确还原的主动/审批时间另外声明不确定性，不把缺失当精确零耗时。

验收：包含多次裁剪的 run 在各关键事件后中断，恢复的投影观测与原事件一致；completed 的正常恢复不变；reset 后不引入旧 task。

## 4. 开发方向：围绕编程任务闭环

### 4.1 仓库上下文与 coding agent 行为

[runtime-context.ts](../src/plugins/runtime-context.ts) 当前注入通用身份、时间、平台和 workspace。下一步增加 coding profile：先检查相关代码及现有变更，遵循项目规则，作最小必要修改，按任务选择检查，并基于真实结果报告。Loop 保持调度职责，项目知识通过插件注入。

项目上下文优先包含仓库根目录、当前工作目录、语言/包管理器的显式配置、可用检查命令及有作用域的 `AGENTS.md`。规则加载要保留路径与来源，按目录作用域应用，限制注入体积；仓库内容不能扩大 Harness 权限。配置可发现，但运行脚本仍须经过既有命令策略和审批。

验收：模型能解释本次加载了哪些规则；根目录与子目录规则作用域明确；非 Git 仓库也能工作；项目规则缺失有合理退化；不能因读取 README/package 配置就自动执行安装或脚本。单文件阅读任务不必先扫描整个仓库。

### 4.2 代码定位、工具输出治理与按需读取

[files.ts](../src/tools/files.ts) 的 `read_file` 读取整文件；`glob`、`grep` 聚合所有匹配，遍历没有默认排除 `.git`、`node_modules` 等目录。Bash 已有 32KiB 截断，但没有完整输出的可回读引用。这会把大量低价值内容带入当前 task；后续只能触发 context_overflow，`/continue` 也无法解决。

先实现确定性方案：

- `read_file` 增加按行范围、字节上限与后续读取位置；必须明确说明只返回了部分内容。
- `grep/glob` 增加结果上限、分页、默认忽略及显式覆盖，避免首次搜索就遍历依赖和 Git 内部目录。
- 对大工具结果保存完整 artifact，模型收到有界预览、总大小、artifact ID 和继续读取入口；保留原事件或不可变引用，不静默覆盖历史。
- artifact 要有工作区闸门、内容 hash/版本、恢复后的定位方式；保证 UTF-8 边界与工具调用配对，不把截断 JSON 当完整结构。

这是新增工具与持久化契约，实施前需更新现有“完整当前 task”规则的具体含义：事件事实保留完整；模型收到的工具结果从产生时就是明确的有界视图。若进一步压缩已有结果，必须单独定义投影规则。

工程参考：Anthropic 的 [上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 介绍了以文件引用和按需加载减少上下文占用。这支持方案方向，不构成 mini-DSH 已取得效果的证据。

### 4.3 可靠编辑与变更交付

先完善现有 `edit_file` 的错误反馈、变更范围和可审查性。增加统一 diff 展示、修改前内容指纹与冲突检测，再按多处修改任务的实际需要提供小型 patch 工具；不为功能数量同时维护多套含糊重叠的编辑协议。

任务开始记录相关文件基线，保留用户已有未提交修改；结束时展示本次变更清单和 diff。Git 工作区可辅助读取 status/diff，但不能把原有 diff 全部归到 Agent，也不能自动 reset/checkout 清理现场；非 Git 工作区使用文件指纹和受影响文件记录退化。

验收：重复匹配、文件已被用户修改、CRLF/Unicode、patch 部分失败、取消与恢复都有明确结果；逐文件记录成功与失败，不声称跨文件事务。审批展示具体编辑范围，不能只给一句“修改文件”。

### 4.4 命令执行、验证和完成报告

[bash.ts](../src/tools/bash.ts) 已有审批、进程树终止和输出截断。先扩展结构化结果：命令、工作目录、退出码或终止信号、stdout/stderr 引用、时长、timeout/cancel 状态和截断标记。允许的 cwd 必须经过路径闸门；大日志结合 artifact 回读。首版聚焦有界前台命令，后台服务和交互式终端延后。

在此基础上记录 `verification` 证据：检查名称、执行命令、关联修改版本、退出状态、日志引用及未运行原因。采用独立的 `not_run / passed / failed / partial` 验证状态；`run.status=completed` 继续表示运行段完成，只有任务要求的检查在对应修改版本上全部成功才能报告验证通过。验证后再次改代码，相关旧结果必须失效或标记过期。

测试失败后由模型结合错误结果重新定位和修改，仍受当前预算约束；不自动重放写文件或未知结果的命令。预算停止时报告已完成修改、已跑/未跑检查和恢复入口。对只读解释任务，允许带证据回答，无须编造测试步骤。

验收：有一个“失败测试→定位→编辑→重跑通过→输出 diff 与证据”的真实文件/命令闭环；失败、取消、未测试和环境阻塞不能被总结成成功；恢复后明确检查是否仍对应当前文件状态。

### 4.5 小型编程评测贯穿开发

先建立 3 个可自动验收的 fixture：单文件 bug 修复、跨文件行为修改、一次失败后的修复与重测，给工具与流程改动建立基线。随后扩展为 12 个任务：单文件 bug 修复、多文件修改、大文件/日志定位、长任务约束与续跑各 3 个。不要先开发通用评测平台再等待 coding 能力落地。

先从事件导出每次请求的输入估算、实际 usage、来源、输出预留、裁剪任务、停止原因、主动时间和审批时间，形成可机器比较的 JSON 报告。`context/projection` 当前没有 requestId；导出时需要明确顺序关联规则，必要时补上关联字段。

每题都具有已知可通过的参考解、固定初始文件和客观验收器；在隔离的临时工作区运行，检查最终文件/测试结果，并检查未破坏已有行为。验收器保存在 Agent 可改范围之外，避免改掉测试后获得假通过；修改项目测试本身仍可作为正常编程需求，但独立验收不能随之改写。故障注入用例另列，不能混入真实任务成功率。

分两步比较，避免把多个改动收益混在一起：

1. 在能安全容纳全量输入的任务上，用相同执行预算比较“全历史”和“现有完整 task 裁剪”；原始无预算实现只适合离线边界基线，不用于无上限付费运行。
2. 比较“现有裁剪”和“裁剪 + 有界工具输出/按需回读”。保持模型、prompt、任务初始状态、预算和验收器一致；大上下文任务中不能运行的基线如实记录为不可行。

先以 mock 跑通评测框架，再做真实模型实验。探索期可每题一次筛查失败；正式对照每题至少 3 次并报告原始分子/分母、重复间波动和失败案例。该规模只能用于项目内诊断，不宣称行业泛化或统计显著性。

需要报告：独立验收通过率、原有测试回归失败数、编辑/patch 失败率、修复迭代次数、人工介入次数、provider/estimated token 分列、每个成功任务的有效 token 成本（全体试验 token / 成功次数，成功为 0 时不计算）、延迟与停止原因。不能只比较成功样例的 token，也不能让“提前失败所以更便宜”看起来像优化。

按中文、英文、代码、schema 分类计算输入估算相对误差与低估幅度；供应商 usage 的真实样本才能校准估算器。保留 estimator 版本及能力元数据核验日期。不要未经验证套用另一家模型的 tokenizer。

当前 64Ki 输入目标、16Ki 最大输出、2M 累计 token 等都是工程初值，尚无质量实验支持其最优性。先固定它们作为基线，再每次只调整一个因素；仅扩大窗口或提高次数不能证明上下文管理得到改善。

工程参考：Anthropic 的 [Agent 评测文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 强调依据最终结果评判，并结合执行轨迹定位失败。本项目选择少量可自动判分任务，是基于当前规模做的工程取舍。

### 4.6 长编程任务状态与有边界的压缩

只有评测确认“当前任务仍因累积上下文失败”后，再加入可选 compaction。

先做结构化任务状态：目标、项目规则与用户约束、修改文件及指纹、已执行动作、当前失败测试、验证是否过期、待办和证据引用。恢复时比较文件当前状态，不能把日志中的旧检查结果当作重启后仍然有效。再尝试以摘要加最近完整工具组替代更早工作集；system、原始当前请求和 unresolved/unknown 工具组必须保护。

这明确改变 R-03/D-02“当前 task 所有 run 原文全部进入请求”的规则，不能作为小优化直接塞入。应版本化策略、保存覆盖事件范围与摘要来源；压缩请求本身也计次数、时间与 token，并预留压缩空间，失败时安全回退。增加约束丢失、事实幻觉、跨恢复摘要失效的测试与评测。

### 4.7 保持 mini 范围

- **预算体验：** 可配置耗尽预警、重复相同失败工具调用的诊断；如需 task 总额度，新增显式策略，不能悄悄给 `/continue` 加总上限。费用预算只有在价格版本、缓存/reasoning 口径明确后再做。
- **状态索引与性能：** `project()` 每移除一个任务就重建与重估；恢复多次 `.some/.filter` 扫描，可能在大日志下出现高开销。先测 1K/10K/100K 事件的恢复、投影延迟和内存，再决定索引、缓存或 snapshot。现有 benchmark 只测追加和读取校验，不证明完整恢复快。
- **维护性：** Loop 的投影规划、usage 结算、工具批次和终态收尾可逐步提取职责；格式和 lint 单独提交。修正 PLAN/PROGRESS 中混在当前状态里的旧时态，不为展示重写全部历史。

保留 Cordis 的服务注入和插件释放，coding profile、仓库上下文、编辑/验证工具围绕现有边界增量实现。MCP 仅用于确实需要的外部文档或开发工具，不把增加接入数量作为主线。短期不扩展通用业务工作流、Web 平台、多租户、多 Agent 调度、向量记忆或大量模型适配。
