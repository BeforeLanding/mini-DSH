# NX-50：PR5 组件优化的真实模型版本对照

状态：零付费准备。协议 ID 为 `NX-50-component-ab-v1`，只用于旧版/优化版的开发对照，不并入 NX-42 的校准或正式批次。运行前必须从两个干净 HEAD 分别生成 manifest；本阶段真实模型请求为 0，付费执行需单独金额授权。

## 为什么做这一批

PR5 的三项组件优化只有离线探针证据：工具预览尾部/额度、摘要可见性投影、交付报告重复读盘。离线读数证明信息保留与资源效率，不证明真实模型解题效果。本协议用同一模型、同一装配、同一整题预算，对比：

- 旧版：`main` 的产品源码提交 `74f8e89721820ef514e26df71cbb05e0c69683c7`。
- 优化版：PR5 的产品源码提交 `0b24b32f1e739d20a015faba49869c72541d5a8c`。

两边都带同一份评测协议代码；每边的工作树 HEAD 因此是各自产品提交之后的评测提交，manifest 同时记录 `sourceBaseCommit`（被测产品代码）与 `gitCommit`（实际执行 HEAD）。

## 装配与整题预算

只跑 `context` 一条臂，它最接近生产默认：输入目标 65,536、主动压缩、16 KiB 有界工具预览、`live` 提示布局。旧版和优化版使用逐字相同的臂配置、工具 schema、权限、自动审批、隔离运行器与验收器。

每个 episode 共享：

- 最多 64 次模型请求（主请求与摘要合计）；
- 128 次工具调用；
- 累计 1,000,000 token；
- 600 秒主动时间；
- 单条输出上限 16,384 token，最小输出预留 4,096 token；请求超时 180 秒，Bash 30 秒。

六题 × 两次重复 × 一臂 = 每版 12 个 episode。每版理论 caps 为 768 次请求、1,536 次工具调用、12,000,000 token、7,200,000 毫秒；block 大小为一，因为每块只有一条 episode。

模型合同：`deepseek/deepseek-flash`，预期回显 `deepseek-flash`，版本 `DeepSeek-V4.1-Flash-1017`，`thinking: enabled`，1M 窗口，`1m` 档，`provider-default` 采样。适配器不发送 temperature 或随机种子，不能宣称解码已固定。执行前须再次核对官方[模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)及[思考模式参数](https://api-docs.deepseek.com/guides/thinking_mode/)。

价格快照（2026-10-25 峰值）：缓存命中输入 `$0.006`、未命中输入 `$0.30`、输出 `$1.20` 每百万 token。保守预留按每条 1M token 全以最高价计，再留 20% 余量并加一次最大请求：每条 `$1.7596608`；12 条加协议探针 `$0.0196608`，单批最低 `$21.1355904`。建议单批金额上限 `$22`；两批合计不超过 `$44`。这是保守门槛，不是预计账单，也不是供应商账单。

## 顺序、冻结与证据

顺序 seed 为 `20261025`，只固定题目与重复的顺序，不控制模型采样。每题重复编号从 0 开始；每版按该种子打乱题目，每个题目一个 block。固定顺序为：

```text
01 R04/0  02 U02/0  03 F01/0  04 F02/0  05 T04/0  06 B03/0
07 F02/1  08 B03/1  09 R04/1  10 T04/1  11 U02/1  12 F01/1
```

每版独立冻结、独立证据目录：

```sh
pnpm eval:v2-freeze --config <config.json> --output <manifest.json>
MINI_DSH_V2_RUNTIME='D:\Agent\tmp\nx42-runtime\unpack' \
  pnpm eval:v2-run --manifest <manifest.json> --validate-only
```

`--validate-only` 不读取密钥、不调用模型、不创建证据目录。冻结文件必须来自干净 HEAD；manifest 记录题目全部文件哈希、隐藏验收哈希、模型/版本、价格快照、预算、顺序、`sourceBaseCommit`、`gitCommit` 与工具 schema SHA-256。

两版 manifest 必须满足：协议、任务、episode 顺序、臂、重复数、种子、tier、窗口、模型/回显/版本/thinking/采样、价格快照与工具 schema 逐字相同；只有 `sourceBaseCommit`、`gitCommit`、`src/**` 与已知的 `package.json` 脚本差异允许不同。其他差异拒绝比较。

每个 episode 保存独立 session、阶段快照与候选退出后的隐藏验收读数。`runs.jsonl` 逐行落盘；`report.json` 记录固定计划分母、token/provider 覆盖、请求/工具/错误、主动时间、压缩与预览截断读数，以及批次起止时间。原始 prompt、模型输出和工具正文不写入公开仓库。

## 预注册门槛

两批都必须是固定计划 12/12 执行、无 missing/invalid、无 `stopped`。任一基础设施/provider/usage 未知或证据异常即批次 incomplete，不作结论，不补跑，不缩小分母。

在完整批次上按 `taskId/repeat` 配对，比较：

- **可靠完成**：`completed` 且四组合同全过、产物验收通过、受保护文件未改、证据完整。
- **产物验收**：退出快照的独立验收通过（即使预算停止也单列）。
- **token**：provider 覆盖的 `input + output` 总量；estimated 必须为 0。
- **主动耗时**：episode 累计主动墙钟。

容差（开跑前固定，不得看结果后放宽）：

1. 新版可靠完成数不低于旧版减 1 条 episode；
2. 新版产物验收数不低于旧版减 1 条 episode；
3. 新版 token 总量不超过旧版 1.15 倍；旧版为 0 时要求新版也为 0；
4. 新版主动耗时不超过旧版 1.15 倍；旧版为 0 时要求新版也为 0；
5. 单题两次新版都失败、而两次旧版都成功（可靠完成或产物验收任一）时，状态为 `review-required`，先审该题轨迹，不能只因总量过关就合并。

状态优先级：`incomplete` > `fail` > `review-required` > `pass`。只有 `pass` 才 `mergeEligible`。这是 12 条/版的开发门槛，不宣称统计显著性、泛化或因果；token/耗时也不作速度因果结论。

## 批次顺序与授权边界

建议先跑优化版、再跑旧版：若候选批次在基础设施层面失败，可尽早停止，避免把另一批也花掉。两批串行，时间戳完整记录；供应商缓存可能跨会话共享，本协议不控制，也不把 cache-hit 计作总 token 下降。

本阶段只完成代码、测试、冻结与 `--validate-only`。在取得**该批次单独金额授权**前，不执行 `--execute`、不读取 API key 发请求、不做协议探测、不创建付费证据目录、不合并 `main`。第二批（旧版）与任何复跑都需要新的授权。
