# NX-51 三项组件的逐项消融设计（2026-10-25）

状态：**只有设计，未冻结、未执行、未授权**。本文件不产生模型请求，也不改变 NX-50 的门槛或结果。任何付费批次都需要单独的金额与批次授权；首次执行与复跑分别确认。

## 要回答的问题

NX-50 只验证了“三项组件一起上”不越过可靠完成/产物验收/token/耗时的预注册容差，`gate=pass` 不等于任何一项组件有正贡献。逐项消融要回答：

1. 去掉某一项组件后，真实任务的输出 token、主动耗时、请求数、摘要次数是否变差？
2. 变差是否伴随可靠完成或产物验收下降？如果只是更快但更容易失败，不算收益。
3. 三项组件的方向是否一致，还是互相抵消（例如预览保留尾部让模型少回读，却让上下文变长、更早触发摘要）？

## 设计：leave-one-out

以“三项全开”为参照，对每项组件各做一个只回退该项的版本。这样每一项的读数是**在另外两项仍开启时的边际贡献**，比 additive（P、P+S、P+S+R）更接近“这项值不值得留”，也避免把顺序效应当成组件效应。

| 臂 | 预览头尾共享额度 | 摘要可见性投影 | 报告查询共享文件版本 | 其余源码 |
|---|---|---|---|---|
| `full` | 开 | 开 | 开 | NX-50 候选 + NX-51 裁剪时序 |
| `no-preview` | **关** | 开 | 开 | 同上 |
| `no-projection` | 开 | **关** | 开 | 同上 |
| `no-report` | 开 | 开 | **关** | 同上 |

- 预览臂：回退 `00c8e32` 与 `14a0d1c` 的行为（保留 NX-50 之前的预览截断方式）。
- 投影臂：回退 `cd17cbc` 的索引实现，恢复逐事件扫描；可见输出必须与优化版逐字相同，只允许资源量不同。
- 报告臂：回退 `fda47d0` 的查询内文件版本共享，恢复按检查条目重复读盘；报告证据字段必须不变。
- NX-51 的“摘要后裁旧任务”在四臂中都开启，作为共同背景，不参与本次三项归因。若它尚未合入，则四臂都不带它，不能只给某一臂加。
- 四臂的 tool schema、系统提示、`context` 臂预算、模型、thinking、采样、窗口、价格快照必须逐字相同；manifest 只允许 `sourceBaseCommit`、`gitCommit`、`src/**` 与已知 `package.json` 脚本差异。

## 任务与预算

- 沿用 NX-50 的六道开发题：`U02`、`B03`、`F01`、`F02`、`R04`、`T04`。它们已经被 NX-50 曝光，因此本批只能作**开发期归因**，不能宣称正式留出集或泛化。
- 每题 2 次重复，四臂共 **48 个 episode**。顺序用固定 seed，按 `task/repeat` 配对比较；每臂独立冻结 manifest。
- 整题预算沿用 NX-50 `context` 臂：65,536 输入目标、主动压缩、16 KiB 有界预览、`live` 提示布局、64 请求、128 工具、1,000,000 token、600 秒主动时间、单条输出 16,384。
- 模型合同沿用 `deepseek/deepseek-flash`、`DeepSeek-V4.1-Flash-1017`、`thinking: enabled`、`1m` 档、`provider-default`；执行前重新核对官方价格与 thinking 参数。

## 金额

按 NX-50 的保守算法，每条 episode 上限 `$1.7596608`，48 条加四次协议探针约 **$84.54**；建议单批金额上限 **$88**。这是最坏情况储备，不是预计账单：NX-50 两批 24 条的实际 usage 估价合计约 `$2.61`，同模型同装配下 48 条的预计量级约为 **$5**。供应商价格、缓存命中与轨迹长度都会改变实际值；报告只引用 provider usage 重算的估价，不把估价当账单。

## 预注册读数

每个 episode 必须保留固定分母，missing/invalid/`stopped` 不补跑、不缩小分母。报告至少包含：

- 可靠完成（`completed` 且四组合同、产物验收、受保护文件、证据完整）与产物验收；
- provider 覆盖的 `input + output`、输出与推理 token、cache-read（不当作总 token 下降）；
- 主动耗时、逐请求耗时、模型等待、摘要次数/耗时/token、工具调用/错误、预览截断、压力压缩；
- 每项组件的 `full - no-X` 配对差值，按题与重复分别展示，不只给聚合。

归因用描述性规则，不设“显著性”门槛：

- 去掉 X 后，聚合输出 token 或主动耗时变差 **≥5%**，且可靠完成/产物验收没有比 `full` 多出 1 条以上 episode，记为 **`signal`**；
- 变化 <5% 或方向在两次重复间相反，记为 **`no-signal` / `inconclusive`**；
- 去掉 X 后更省 token/时间但可靠完成下降，记为 **`efficiency-tradeoff`**，不能算组件收益。

5% 是诊断阈值，不是统计显著性；48 条只够开发期排序，不足以为正式题库下结论。

## 执行顺序与边界

1. 先确认 NX-51 裁剪时序是否合入；四臂必须共享同一决定。
2. 为四臂分别从干净 HEAD 生成 manifest，并做 `--validate-only`。任一步失败即停止，不发起模型请求。
3. 先跑 `full`，确认装配与证据目录正常；再按固定 seed 顺序跑三个回退臂。任一批次 incomplete 即停，不用另一批补齐。
4. 付费前单独列出模型、任务、重复、金额上限与证据目录，取得**该批**授权；复跑需重新授权。
5. 不合并 main、不发布、不改写 NX-50 或 NX-45 的原始证据。

## 与 NX-51 时序修复的关系

NX-51 的诊断与修复针对的是“摘要后旧任务不清、同一 run 反复摘要”，与三项组件的开关正交。建议在组件消融之前先用一个小批次验证时序修复本身的收益，否则组件对比会把“摘要次数从 3 降到 1”的收益算到组件头上：

- 单独两臂：`prune-after-summary` 开/关，同一模型、同一六题、各 2 次（24 episodes）；
- 只在这两臂上读摘要次数/耗时、输出 token 与主动耗时；其余三项组件保持不变；
- 若摘要次数没有实际下降，或摘要下降但可靠完成下降，则不把时序修复作为默认行为推广。

这一小批同样需要单独授权；在授权前只保留设计。
