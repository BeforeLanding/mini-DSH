## 当前实现
## NX-06 决策
- 请求 trace 从当前 reset epoch 的 confirmedEvents 派生，不新增生产事件版本。以 model/start 为分页单位，用 requestId 关联 model/end/model/usage；用相邻 model/start 形成有界事件区间，关联该请求产生的 assistant/message 或 assistant/tool_calls、tool/start/result、file/change 和 verification/start。重复 toolCallId 按当前请求区间隔离，不能跨请求误配。
- trace 返回 sessionId/taskId、offset/nextOffset/eof/total；每条记录返回 runId、模型、run 状态/停止原因、上下文投影、usage、完成性、响应种类及工具结果摘要。文件与检查只返回 changeId/verificationId 引用；不复制用户提示词、模型正文/推理、工具参数、工具结果正文或命令日志。完整原始事件仍由 /history 提供。
- task_report 沿用 NX-15 的文件和验证双分页，在顶层增加 sessionId/currentRunId、task counters 与按 run 排列的模型、前序 run、状态/停止原因、counters、usage 和起止时间。数据以已确认 run/finish 为准；未结束段明确 running，不能用内存中的未确认状态冒充持久事实。
- 模型使用 request_trace 工具；CLI 使用 /trace [requestOffset] [byteOffset]，正文继续受 maxChangeOutputBytes 限制并按 UTF-8 字节续读。查询只读，不消耗模型/工具预算，不自动写报告文件。分页会重新读取当前事件，不承诺快照一致性。

## NX-15 决策
- Bash 的可选 verification={files:[...]} 显式选择验证；文件路径相对工作区，默认最多 100 个、每个最多 1 MiB（可配置），复用 NX-13 有界 UTF-8 快照、missing 与 SHA-256 和真实路径。只保证声明范围，依赖/目录新增及检查中改后恢复等未观察变化不能自动证明。
- 新增 verification/start 与 verification/result，保持事件 version=1 与已有 run 终态。start 包含 verificationId、command/cwd、可选 toolCallId、files 的 path/hash/location；落盘后才能启动命令。result 包含原始有界 CommandResult 和检查后 files；检查后快照错误记录为 unavailable，不能把零退出误报通过。取消或崩溃可以留下 unknown，不重放。
- 结果与意图严格一一配对、task/run scope 校验；取消清理的迟到结果允许属于原 run。查询仅用 confirmedEvents，重新核验声明路径、hash/location，并标记后续文件工具修改（即使改回原字节）。已完成检查的退出状态与当前版本分开显示；同 task 所有失败保留。没有全部任务验收自动标记。
- 报告分页验证记录并显示文件工具变更、未覆盖文件和 runStatus；模型与 CLI 均使用只读查询。文件范围和输出限额可配置；日志随验证结果持久化，Bash 工具结果继续提供 NX-14 引用。不增加后台执行或付费模型调用。

## NX-14 决策
- 使用独立前台执行核心，Bash 插件仍负责输入、路径与审批。结果 version=1/type=command，状态为 exited / spawn_error / timed_out / cancelled；exitCode 与 signal 保留实际 close 值，时长从 spawn 前单调计时，不包含审批。
- maxCaptureBytes 为两流共享字节额度；分别标注截断，UTF-8 边界不完整尾部舍弃，非 UTF-8 字节替换解码。timeoutMs 是插件配置，不由模型扩大。cwd 默认为 sandbox.workspace，可指定工作区内现存目录；真实路径在审批后复核，应用策略不承诺 OS 隔离或消除所有外部竞态。
- 工具 output 增加可选 isError 分类，不以抛异常丢失已执行结果。大命令日志逐流投影，使用既有 ToolResultStore/read_tool_result；每流保留预览及 ref/存储截断，元信息不被整段日志预览覆盖。取消后不使用新 signal 绕过取消写存储；留下有界日志和明确存储错误。
- 沿用现有 tool/result JSON 文本，不修改事件版本；run completed 仍只表示运行段结束，命令退出 0 不是任务验收。
- run 的主动超时/取消先结束等待时，沿用 unknown 结果，不等待命令清理来改写唯一终态；直接工具调用的取消结果在进程 close 后返回结构化 cancelled。unknown 恢复不重放。取消后日志存储不得绕过已取消 signal。

严格 TypeScript / NodeNext 编译产物运行；Session 使用版本化 JSONL 事件恢复；Loop 实现上下文投影、执行预算与同 task 续跑；DeepSeek 归一化 usage 并限制输出；CLI 提供 /budget、/continue 和 session 恢复。原始基线及逐步变更保留在 PROGRESS。

## 小步开发与提交流程
用户要求每完成一小部分就提交一次。一个步骤应只有一个主要目的、有可观察结果、能独立验证和回退；一个 CB 任务可以拆成多个提交，不能只按整项任务或里程碑提交。

**执行门槛：当前小内容验证通过、证据回填并提交后，才允许开始下一个小内容。** 此要求适用于所有 CB/NX 任务及一次请求中的多个开发内容。开发前在 TASKS 列出子步骤、对应验收及提交边界，并向用户说明；用户要求完成整个任务，不表示可以合并该任务的全部变更为一次提交。

提交前逐项核对 diff 是否包含多个可独立验证或回退的结果，若包含则拆分；拆分以行为和验收为依据，不以文件数或行数为唯一标准。每个小内容的实现、直接相关测试和必要文档放在同次提交；验证失败先修复或记录阻塞，不继续叠加下一项功能。完成时在 TASKS/PROGRESS 记录实际子步骤提交，保留已有历史，不通过自动重写提交伪造小步记录。

例如 NX-05a 应先交付最小隔离运行/验收支撑及首个 fixture，再分别增加第二、第三个 fixture，之后独立交付模拟模型的真实工具闭环及额外验收失败边界；每步验收后立即提交。此前 f06cbfb 将这些内容集中在一个提交中，作为粒度过大的反例保留；今后不能仅因它们都属于 NX-05a 而再次合并。

每步循环：选定子步骤及验收 → 更新任务为进行中 → 实现并补必要测试 → 执行针对性检查及适用回归 → 查看 diff → 回填 TASKS/PROGRESS → 本地提交 → 报告提交号、验证与下一步。代码、相关测试和进度同次提交；不能先提交失败测试作为已完成工作。

建议提交切分（每项至少一个，按实际复杂度继续拆）：
1. 恢复依赖和原测试基线。需要仓库变更才提交；仅安装或执行检查时提交必要验证记录，不制造无意义代码变更。
2. CB-15a：引入并锁定 TS 工具链，建立编译产物执行路径，旧 JS 行为保持；验证入口、配置和原测试。
3. CB-15b：迁移 core/类型契约；CB-15c：迁移 plugins/models/tools；CB-15d：迁移测试并收紧配置/CI。每批构建和原行为回归通过再提交，不与预算功能混合。
4. CB-01/02：配置校验与覆盖规则、任务/run 事件与唯一终态分别提交。
5. CB-11：串行追加/锁、写入失败、损坏恢复分别提交；CB-03：usage/输出限制；CB-12：重建与 unknown 识别。
6. CB-04/05：估算、完整分组、请求投影与容量停止分别提交。
7. CB-06/07/08：次数限制、主动时间/审批/取消、累计 token 分别提交。
8. CB-13/09：续跑核心、CLI 继续/预算状态分别提交。
9. CB-10：跨模块恢复与停止回归、CI/用户文档和最终验收分别提交。

普通步骤跑对应测试；修改公共契约/装配、完成迁移批次或阶段时跑类型/构建与完整测试。跨平台结论必须有实际 CI 证据，用户已授权每个小步提交后推送到 origin。提交标题写清本次结果，可采用 docs/chore/refactor/feat/fix/test 前缀。已完成提交保留，不自动 squash/amend/rebase。

## NX-13 编辑与交付决策

- 文件快照默认限额 1 MiB，可配置；完整字节指纹区分 missing 和空文件。读取大文件保留分段行为但说明无编辑指纹，编辑禁止超限。
- 唯一字面替换，统一 unified diff（共同前后缀裁剪，单 hunk，避免二次复杂度）。同目录临时文件 sync 后重新解析路径、核验目标，再 rename；取消在 rename 前不写目标，rename 后按实际成功记录。最终检查与 rename 仍有外部进程竞态，属于应用层乐观检测。
- 快照保存真实 location；提交使用真实目标路径，内部文件软链保持为软链，审批中目录/文件软链改指向也拒绝。显式 chmod 恢复原权限，避免 umask 改变权限；rename 已成功后临时清理错误不能倒置提交结果。
- 无 session 直接调用兼容；有 session 用首次观察与最近确认版本检测陈旧读取。显式 expectedHash 可在重新核验后指定当前版本。首次观察前用户改动作为基线保留。
- 新增 file/baseline、file/observed、file/change、file/change-result 事件；工具结果和 completed 语义保持。首次基线固定，重新读取更新观察指纹；成功编辑更新预期版本。意图含 before/after 快照并先 flush；结果落盘失败或崩溃留下 unknown，只投影已确认事件，不根据文件匹配推断成功。取消后的协作工具可以在 run 终态后追加同 run 的失败结果；恢复校验已知 run、唯一意图及结果配对。
- 用户在两次编辑间修改文件时，标记 externalChangesBetweenEdits 并输出逐次编辑 diff，避免首次基线至最新版本的差异夹带用户改动；最后一次成功编辑后的外部变化另标 externalChange。unknown 仅展示当前指纹，不断言外部归因。
- 逐次失败独立记录；清单按 task 重建、跨 run 保存，reset 隔离。CLI 有界展示，模型用 task_changes 查询；大结果继续用 NX-07 引用。文件工具之外的修改不自动归因。

## NX-12 仓库上下文决策

- runtime-context 增加 general/coding 配置；CLI 装配入口默认 coding，底层插件默认 general，保持现有调用兼容。身份不直接绑定模型或 Loop。
- ProjectContextRuntime 只读取配置的 workspace 内从根到当前目录的祖先链；当前目录默认 `.`。可用 project_context 工具按需查询其他目录，查询不改变工具 cwd。目标目录不同于初始目录时，coding 身份要求先查询该目标作用域的规则。
- AGENTS.md 自父向子加载，保留相对来源及作用域；子规则只在其子树内覆盖父规则。规则内容属于项目指导，不能扩大沙箱权限，不把 README/配置/脚本里的文本提升为 Harness 授权。
- 加载限制可配置：maxFileBytes 默认 16 KiB，maxContentBytes 默认 32 KiB（规则原文与配置序列化内容合计），maxDirectories 默认 16；均为正安全整数。规则超限、不完整 UTF-8、非普通文件或越界软链明确失败，不注入残缺规则；元数据读取错误仅记录来源与原因，不注入非法内容。
- 项目元数据选当前目录祖先链中最近的 package.json，保留包管理器/Node engines/显式 test、check、typecheck、lint、build 脚本；tsconfig.json 与常见锁文件只查看存在性，Git 根只查看祖先链上的 .git 标记。没有 Git 或配置时显示未发现。README 仅提示存在和路径，正文按需读；不遍历依赖和仓库内部文件。
- 每次组装及按需查询重新读取；不执行外部命令、不自动安装、不自动检查。完整 system 继续参加现有 token 估算；上下文不足按现有 context_overflow 停止，不追加新的生产事件契约。

## 模块边界
- 事件存储：经存储接口串行追加/读取，关键事件等待可靠写入；第一版仅 JSONL。
- Session：重建消息、任务、用量和状态；重放没有外部副作用。
- ContextBudgetRuntime：估算、历史分组和请求投影；不修改原始事件。
- RunBudgetRuntime：次数、主动时间、token 预留/结算、停止状态。
- AgentLoopRuntime：协调请求投影、调度检查、响应结算、工具结果和资源清理。
- LlmRuntime / 适配器：传递输出上限，返回 usage/finishReason，保存 provider 所需 reasoning。
- Cordis 插件：服务装配、配置注入、注册释放；CLI 消费状态，不承担预算算法。
- 成功 agent.send() 仍返回字符串；停止拟采用带原因与状态的类型化错误，具体类型在 CB-01 实现时定稿。

## 设计决策及取舍

本节是技术取舍与默认参数的**唯一维护位置**。五条关键选择（事件与投影分离、协议完整性、可靠编辑、验证时效、未知副作用恢复）的替代方案、代码锚点与测试锚点另见 [设计取舍](DECISIONS.md)——那份文档是本文的非规范性说明，不重复这里的决策与数值，改决策请改这里。

### D-01 范围
第一版包含 TypeScript、上下文投影、四类执行预算、JSONL、session 恢复和 /continue。摘要、长期记忆、费用预算和任意程序位置精确恢复不纳入；见需求文档。

### D-02 原始事件与请求投影
原始历史完整保存；请求只选择可容纳的完整旧任务/轮次，完整保留 system、安全规则和当前 task 的所有 run。过长停止，不自动摘要或截短当前过程。
替代：全量发送无法控制规模；最近 N 条可能切断工具协议；摘要/检索增加生成误差与新依赖。当前选择确定且可测，代价是旧信息可能不可见、长任务可能停止。

### D-03 计数与兼容
请求计实际进入模型适配器的调度（含失败和最终回答）；工具计进入执行入口的调度（含拒批和失败）；skipped 不计。底层未注入预算策略的旧调用兼容无上限；CLI 注入有限默认策略。
替代：只计成功会纵容无限失败循环；只限制 loop 无法约束单批工具数量。次数和实际用量分别记录，不自动重试。

### D-04 Token 与模型协议
每个候选历史集合先依据输入估算及 run 剩余额度计算实际输出预留，再检查容量；保留可行历史优先于按配置最大输出预留裁剪。最低输出不足、输入目标或窗口超限时，才移除下一组旧完整任务并重算；最终仍按 token 优先于 context 的顺序停止。
以实际 usage 结算，估算及输出预留用于请求前判断；缓存输入仍计 token，reasoning 是输出细分，不重复加算。缺少 usage 时估算已知输入/接收输出并标记不确定，不记零。适配器必须处理无新文本的流末包。
供应商能力按 endpoint/model/核验日期记录，不凭模型名猜窗口；不承诺严格计费上限。保留模型协议字段，包括无工具最终回答的 reasoning。

### D-05 时间与终态
回答、用量等执行事件先在主动预算内完成 flush 并复查，再生成唯一 run/finish。终态提交确认同样受剩余主动时间约束，且另受 finalizationTimeoutMs（默认 5000ms、可配置）限制。停止后的错误收尾仅使用该独立上界，保留原停止原因；成功确认后再次复查取消/deadline 才返回答案。

终态写入开始后不能安全撤销，也不能追加相冲突的第二个终态。确认超时、取消或失败时，调用失败；当前进程暴露 terminalCommit.status=uncertain、终态快照及实际观测主动时间，禁止新 run，迟到写入不会改回 completed。须关闭并重新读取日志判定持久化事实：若唯一 completed 记录确已完整落盘，恢复按 completed；若未落盘，恢复按 running 崩溃窗口处理。run/finish 的计时为提交前快照，terminalCommit.activeDurationMs 为当前进程包含提交等待的观测值；重启无法精确重建最后 sync 时间。收尾上界不保证物理取消文件 IO。
用单调主动时间和组合 AbortSignal，审批暂停主动计时且单独超时；结束清理 timer/监听器。Promise.race 只停止等待，不替代取消。
同一 run 仅一个终态；已封存状态不被迟到回调覆盖。检查顺序：用户取消 → 主动 deadline → 对应调度次数 → token → 上下文容量。最后允许的完整回答可完成；超出 token 额度则停止后续调度。
非协作工具可能继续运行，不能保证物理终止；结果不确定标 unknown。

### D-13 环境展开与命令内绑定
判据同上（D-12）：「这段文本会不会被 shell 展开／执行」，不取出现位置。`$NAME`／`${NAME}` 的展开**按 shell 的引号与转义语义**决定——单引号内不展开、`\` 之后的下一个字符不参与展开（`\$` 是字面量；`\X` 整对复制，因此 `\\$` 里的 `$` 仍会被展开），双引号内与裸词照旧展开。`~` 走同一趟扫描。展开仍产出**同一条 `expanded` 字符串**（逐字复制不替换的字符，含反斜杠与引号），因为下游的 token 偏移（`tokens[index].index`、`expanded.slice(...)`）与 `..` 整串正则、片段抽取全部建立在这条串的原样形状上。
**同一条命令串里由 shell 自己绑定的名字优先于 `process.env`**：`for NAME in <词表>` 与 `NAME=<字面量>` 会被收集。`for` 的候选值必须**逐项**通过形状判定（不是绝对路径或盘符、不含 `..` 分量、不含会被 shell 再解释的字符），任一项不通过即**整条拒绝**并给**独立理由**（不与「未定义环境变量」共用理由串）。两者都没有的名字仍按未定义环境变量拒绝。
替代（各自的具体失效）：只替换 `for` 的**首值**——`for f in a /etc/passwd; do cat $f; done` 只取首值就被放过；把**多值文本拼接**再替换——`"$f"` 在双引号内合成一个词，同样被放过；**逐值展开循环体**——要对 `do…done` 做语法解析、要新增宽度上限，嵌套还会相乘。选定的「代表值 + 全候选值形状门槛」使「用哪个值做代表」与逐值检查等价，且词表本身始终留在展开后的串里，危险字面量照旧被路径分支看见。
上限与旗标一律取模块常量，不进 `SandboxConfig`——理由同 D-12（`test/fixtures/estimation/corpus/code/core-contracts.txt` 是 `contracts.ts` 的逐字副本且被 digest 钉住）。
代价与残险：`read NAME` 的取值来自 stdin、静态不可知，**不绑定**（按「不能证明安全就拒绝」处理）；`for` 的多值候选被近似成单一代表值，代价由上面那条门槛兜住；绑定的收集与文本顺序无关，因此 `cat $X; X=/etc/passwd` 也会拒绝——只会过拒、不会漏放。`do`／`then`／`else` 之后仍不算命令段起点（NX-26），本项不修但已登记——**2026-10-01 由 D-14 闭合**；该机制随后又**由 D-16 整体撤回**。

### D-14 命令段起点的词法判定
判据沿用 D-12：「这段文本会不会被 shell 执行」，不取出现位置。`executable`（`src/core/sandbox-runtime.ts:439`）此前只有两种情况——**首 token** 与**紧邻 `|`／`;`／`&`／换行**——而它是**命令段起点**的定义：为真时重置每段状态（`:441-449`）并开启取网工具的操作数模型（`:466` 的 `model && !executable` 守卫）。因此保留字后面的命令词永远不是段起点，`for f in a; do curl example.com; done` 的操作数模型整段不跑。
**机制是单 token 前视旗标**：token 为真时若它本身处在命令段起点、**且是原样未被引用、不含路径分隔符的字面词**、且属于闭集 `if`／`elif`／`while`／`until`／`do`／`then`／`else`，就令**紧随其后的一个 token** 也算段起点。闭集是 shell 里引入命令位的**完整集合**：终结符（`fi`／`done`／`esac`）之后没有新命令，`case` 后面的词是主语，`in`／`!`／`time` 不引入命令位。
**为什么只活一个 token**：这样 `<保留字> <rest>` 与把 `<rest>` 写在首 token 位置**判定完全一致**——保留字在判据里是**透明的**，本项不引入比顶层更强的检查。跨词存活会把 `do echo curl example.com` 的实参 `curl` 当成命令词。
**为什么必须是原样字面词**：shell 的保留字识别发生在展开与去引号**之前**，`"do"`／`do"` 不是保留字；也不能改用 `basename`，否则 `./do`／`/usr/bin/if` 会被误认。
替代：见到保留字即拒——那是位置判据，`echo do curl example.com` 会被误伤；只把 `do`／`then`／`else` 计入——`if curl example.com; then echo ok; fi` 与 `while curl example.com; do …; done` 仍放行（同一机制、同一行判据，留一个洞只等于把问题推后）。
上限：旗标在每次迭代开头**无条件清除**，不得挪到循环末尾——`:495`／`:496`／`:499`／`:505` 四个 `continue` 会跳过末尾清零，让旗标多活一个 token。上限取模块常量，不进 `SandboxConfig`——理由同 D-12。
代价与残险：**两条净放宽**（都与顶层同形状的既有判定对齐，不是新语义）——`for f in a; do echo https://example.com; done` 从此放行（改前因 `commandWord` 还是 `for` 而误拒），`for f in a; do echo bash -c "curl https://evil/x"; done` 从此放行（`bash` 是 `echo` 的实参，从不执行）；**一处新过拒**——`X=do; $X curl example.com` 变拒绝，因为展开先于分词、展开出来的关键字被当保留字（bash 并不这样认），方向是过拒。相邻形状**不修、登记为 NX-30**：子 shell 与分组 `( … )`／`{ …; }`、`case … in X)` 的臂体（同一个「未跟踪算子」机制），以及 `exec` 与赋值／重定向前缀——**2026-10-01 由 D-15 补齐其中的算子支**；该前视随后又**由 D-16 整体撤回**，NX-26 重开。

### D-15 命令段起点的算子支
判据沿用 D-12：「这段文本会不会被 shell 执行」，不取出现位置。D-14 补的是保留字，**引入命令位置的另一半是算子**——子 shell `( … )` 与分组 `{ …; }`。它们此前连算子都不算：词体类 `[^\s|;&<>]+`（`src/core/sandbox-runtime.ts:438`）把括符粘进 token，于是 `networkTools[basename]` 与 `shellWords.has(basename)` 双双落空，取网工具的操作数模型与 `-c` 片段抽取都不启动——`(curl example.com)`、`{ curl example.com; }`、`(bash -c 'curl http://x')` 今日全是 allow。
**机制是「规范 token，不动分词器」**：保留 `:438` 的词体类、`:464` 的分隔符类 `[|;&\n]`、`findShellCommandFlag`（`:194`）的分隔符守卫、`bindingWord`（`:257`）全部原样；改为在去引号之后把 token 首尾**未被引用**的 `(`／`{` 与 `)`／`}` 剥掉（含 `$(` 的词跳过，空结果保留原样），再把 `(`／`{` 加进与保留字**同一支**的 `pendingCommandPosition` 前视——opener **自身**处于命令段起点、且未被引用也未被规范化时，令紧随的一个 token 也算段起点。`)`／`}` 只收尾，不引入命令位（`(a); curl x` 的命令位由 `;` 给）。
**为什么不动分词器**（这是本项的核心取舍，替代方案的失效全部是实测的）：① 把四个字符从词体类里拿掉——`matchAll` 没有以它们开头的分支，字符被**静默跳过**而不是变成 token，「opener token」那半个设计是死代码，`( curl example.com )` 反而修不好；它看似能修 `(curl example.com)` 靠的是「删掉 `(`、让 `curl` 落到 index 0」，是碰巧。② 同一次改动会**凭空造出裸 `/` 开头的 token**：`mkdir -p src/{a,b}/x` 被切成 `src/`、`a,b`、`/x`，最后那个是根路径操作数 → `path escapes the workspace`，`echo {a,b}/c` 同理——这是对**普通合法命令**的误伤。③ 把 `(` 加进分隔符类 `[|;&\n(){}]` 会让 `$()` 内的 token 变可执行、`commandWord` 被重置成 `date`，于是 `echo $(date) https://example.com` 由 allow 变 deny（顶层 `echo` 的惰性 URL 豁免失效）。三条合起来：**分词器的下标对齐是下游的承重墙**——`pipedDownstream`（`:477` 用 `start + raw.length`）、`eval` 参数切片（`:561` 按 token 下标）、`-c` 片段抽取全都依赖它，所以宁可规范 token，不改分词。这也使 `:250` 那句「与 #inspect 的分词器同源」的注释一字不改。
`raw === token` 的含义在此自然扩展为「未被引用**且未被规范化**」：`(curl` 规范化后 `raw !== token`，故**不**设旗标——它自己就是命令；孤立的 `(`／`{` 保持 `raw === token`，设旗标，与保留字行为完全对称。
上限：旗标复用 D-14 的单 token 前视与「每次迭代开头无条件清除」，理由同 D-14（四个 `continue` 会跳过末尾清零）。
代价与残险：**四条净放宽**（都与顶层同形状的既有判定对齐，不是新语义）——`(echo https://example.com)`、`{ echo https://example.com; }`、`(printf "%s" https://example.com)`、`(echo bash -c "curl https://evil/x")` 从此放行，改前 `commandWord` 停在 `(` 上，`stdoutOnlyCommands` 豁免与 `-c` 片段豁免都不生效；豁免边界未动（接管道仍拦）。**三条新过拒**，全部落在 shell 语法错误的输入上——`{curl example.com;}`（bash 里 `{curl` 是普通命令名）、`curl (example.com)`、`(curl example.com`（不配对）；与 `cat "/Program Files/secret"` 同一处置，写进用例让它成为**记录在案的决定**。**不修、另行登记**：`case … in X)` 的臂体留在 NX-30 的剩余半（矩阵加 `known gap NX-30 arm body` 一行使其不被静默）；`exec`／赋值／重定向前缀仍在 NX-30 条目内标为未做；**包装命令**（`env`／`nice`／`timeout`／`command`／`nohup`／`xargs`／`find -exec`）与**进程替换** `<(curl x)` 属本轮**新发现**，机制不同（要懂每个包装命令「操作数里哪个才是命令」，是新增一份工具知识表），登记为 **NX-31**。

### D-16 命令闸门的有意收缩（NX-32）
**这是一次方向相反的决策：不再补边界，而是撤回判据。**

判据**不再**是「这段文本会不会被 shell 执行」——那个判据在启发式词法下**没有终点**：NX-26 补保留字、NX-30 补算子、NX-31 又冒出包装命令，后面还有进程替换与 `sh -c` 嵌套混淆；而 `sandbox-runtime.ts` 因此长成 `src/` 里最大的单个文件（576 行，占全部源码 14.6%）。更要紧的是**它在唯一没有审批兜底的地方也拦不住**：`autoApprove` 是评测跑用的模式（`test/coding-fixtures.test.ts:62,377`），那里没有审批，而文档早已写明 `node -e`／`python -c` 的程序字符串不在覆盖内——实测里模型自己写 `node -e` 探针有 75 次。判据改成**「粗形状防误操作」**：只保留廉价、稳定、不易误判的四条（四个整串正则、token 上的路径与 UNC 判定、按段首工具名的出网拦、引号感知的分词）。

机制：出网从「识别工具 → 解析目标 → 比对主机白名单」退化为**按段首工具名整段拒绝**——按 `|`／`;`／`&`／换行切段，段首词的 basename 属于取网工具集合即拒。段界取 **token 之间的空隙**里有没有分隔符，**不按文本切分**（否则 `awk '/stage(7|7)|phase 7/{f=1} f'` 里被引号吃掉的 `|` 会凭空切出一段）。段首谓词保留不删，它有两个用处：出网按工具名的判定，以及 `/bin`／`/usr/bin` 命令词豁免的兜底——**去掉它，`cp foo /usr/bin/evil` 会被那条白名单静默放行**（实测还原得出）。被删掉的：`$(...)`／反引号／`-c`／`eval` 递归抽取与深度/片段上限、按引号与转义语义的环境展开与 `for`／`NAME=` 绑定、保留字与算子前视、三种操作数模型与旗标表、`stdoutOnlyCommands` 惰性输出豁免、`allowHosts`。

代价（全部记录在案，不是意外）：① **NX-23 闭合**（裸 URL 规则随操作数模型一起删除，`--grep <url>` 这类数据不再被当成目标）；② **NX-19／NX-24／NX-26／NX-30 由「已闭合」退回已知缺口**——它们各自的机制已不存在，矩阵里整组降级为欠拦 gap；③ **本地回环不再豁免**，`curl http://localhost:8080/health` 由放行变拒绝，且**没有审批作为逃生门**（闸门 deny 发生在 `approve` 之前），纯本地操作数如 `scp report.pdf backup.pdf` 一并被拒；④ 新增两条 gap：非段首的 URL 操作数（`git clone <url>`）与变量间接（`X=/etc/passwd; cat $X`）。

残险与处置：收缩**不宣称命令闸门变强**，只宣称它变便宜、变诚实——真正的边界是工作区路径闸门（`utils/path.ts` 的 `resolveInside`，本项一行未动）与人工审批。**此后不再为闸门开新工作项**，除非 `.eval-evidence` 回放（782 次真实调用，`nx24-replay-probe.mjs`）里出现新拒绝或实际撞上。

**2026-10-02 由 D-17 局部修订**：保留的四条里只有 `..` 被再切细（从整串正则改为 token 级路径分量判定）。收缩的其余部分——三个整串正则、token 上的路径与 UNC 判定、按段首工具名的出网拦、引号感知分词——一行未动。

语料快照那句话说法的订正：D-12／D-13 写的「`test/fixtures/estimation/corpus/code/core-contracts.txt` 是 `contracts.ts` 的逐字副本且被 digest 钉住」不再准确。**digest 只钉语料自身的文本**——`scripts/estimation-corpus.ts:54` 的 `corpusDigest` 只读 corpus 目录里的样本，从不与 `src/` 比对（本项实测确认）。因此删掉 `SandboxConfig.allowHosts` 不会让 `pnpm eval:estimate` 变红；**该文件自 NX-32 起与源文件不再逐字相同，按「冻结快照」对待**（`test/fixtures/estimation/README.md` 的措辞本来就授权这一点）。约束仍然成立的部分是：**改语料文本**会动 digest 与全部参考 token 数，所以本项不碰它。

### D-17 目录逃逸的 token 级判定（NX-18）
**这是 D-16 之后第一次对保留判据做**局部**修订，方向与那次相反：把一条判据从「整串」改成「token 级」，因此既有净放宽，也有净收紧——两条都记录在案。**

判据：一个 token 判为 `..` 逃逸，当且仅当它的**去引号正文**同时满足三条——① 不含空白；② 按 `[\\/=]` 切分后**存在分量恰为 `..`**；③ 正文含分隔符，**或**它在原串里是裸词。

**为什么只有 `..` 这一条能这么改**：D-16 保留的四条承受的是同一句代价（不区分「数据」与「代码」），但另三条**没有可用的形状判据**——`sudo`／递归删除／管道进 shell 是「文本里出现即拒」的能力判据，改它就得引入「哪个位置算操作数」的子命令知识，而那正是 D-16 撤掉的东西。`..` 恰好有一条：「它是不是一条以 `..` 为分量的路径」。判据取形状、不取出现位置，与 D-12 以来的口径一致。

**净放宽（记录在案）**：引号成词、无分隔符、内容恰为 `..` 的 token 放行——真实语料里那是正则（`grep -n ".."`）。裸 `..` 仍是路径、照旧拒绝，因此**「引号包住裸 `..`」是一种可以绕过的形状**（`cd ".." && cat x`）。这是本条记录的代价，不用「已闭合」之类的措辞。

**净收紧（连带，非本意但可接受）**：`=` 计入分量边界，于是 `X=..; cat $X/secret` 由放行变拒绝（分词把 token 切在 `;` 之前）。**这不是变量间接被支持了**——孪生行 `Y=/etc; cat $Y/passwd` 仍是已知缺口，两条分开记，不合并成「已覆盖」。

**明确不修**：`--grep=..` 这类「`=` 后紧跟 `..` 且无分隔符」的惰性文本仍被拒——它与 `--dir=..` 在形状上无判据可用，按 NX-29 的口径处理：**没有可用的形状判据就不放宽**。

**残险与回放证据**：判据仍是粗形状检查，真正的边界是 `utils/path.ts` 的 `resolveInside` 与人工审批，两者都不是操作系统隔离。782 次真实调用的回放里，含 `..` 的 57 条**只有 1 条被拒**（`062d867579`），而它的根因是**闸门看不见命令内部的 `cd`**（命令先 `cd src`），属 D-16 撤掉的「命令位置状态」一族——**不在本条范围内，本条之后那条拒绝仍然存在**，因此它在 `nx24-replay-probe.mjs` 的断言集合里保留，只订正注记。

### D-18 here-doc 正文按消费者分流（NX-25）
**这是 D-16 之后第二次局部修订，触发条件符合其处置规则**：782 次真实调用的回放有 1 条由 here-doc 正文造成的误拒（同时登记为 NX-28），诊断矩阵另有 `cat <<'EOF'` 的最小复现。目标只是不再把数据正文当成顶层命令扫描，不借机恢复 D-16 撤掉的通用 shell 解析器。

判据：在命令行中识别未被引号包住的 `<<WORD`、`<< WORD`、`<<-WORD` 与带引号定界符；按 shell 的顺序从随后各行配对正文和独占一行的终止词，`<<-` 只为比较终止词与正文扫描去掉前导 tab。每份正文绑定到该重定向所属简单命令的首词：消费者 basename 属于 `sh`／`bash`／`zsh`／`dash`／`ksh` 时，正文是会被执行的脚本，递归走同一条命令闸门；其余消费者的正文是数据，从顶层扫描文本中剥离。命令行本身始终照旧扫描，所以 `curl <<EOF` 仍按段首取网工具拒绝。

边界取**闭集 shell 消费者**，不猜任意解释器：`node --input-type=module <<'EOF'` 的正文对 shell 是数据，交给 node 之后是否执行属于 D-16 已明确不覆盖的「程序字符串／脚本内容」一族；`env bash <<EOF`、变量间接命令名、函数与别名同理不新增包装命令知识。这里修的是已观测误拒，不宣称扩展命令闸门的安全边界。

上限与失败语义：单条命令最多识别 16 份 here-doc，正文累计最多 256 KiB，递归最多 3 层；超过任一上限、缺终止词或出现无法可靠配对的定界符时**拒绝并给独立理由**，不把剩余正文悄悄当数据跳过。上限取模块常量，不进入 `SandboxConfig`，避免为局部词法修订扩大公共配置面。

替代方案：① 整段跳过全部正文会放过 `bash <<EOF` 中真正执行的 `curl`；② 全部递归会保留 `cat <<EOF` 的现有误拒；③ 见到 here-doc 一律拒绝会把已观测的合法模型调用变成稳定过拒；④ 引入完整 shell parser 与 D-16 的收缩方向冲突，且仍需定义解释器与包装命令知识。选定的窄分流只增加「重定向—正文—消费者」这一条已观测语义。

### D-19 Windows Git Bash 的 `/tmp` 挂载映射（NX-27）

**这是 D-16 之后第三次由真实回放触发的局部修订**：782 次真实模型 bash 调用里 4 条使用 `/tmp`，全部在 Windows 被 `node:path` 错解成当前盘根下的 `D:\tmp` 后判为工作区外；Git for Windows 实际把同一 spelling 映射到用户临时目录。判据不能一边按 Bash 语义执行、一边按 Windows 根路径语义审批。

选定「映射挂载点」而不是「字符串白名单」：仅在 Windows、且 POSIX 归一化后仍为 `/tmp` 或其后代时，取 `/tmp` 后的相对部分，以 `os.tmpdir()` 为根再次调用 `resolveInside`。因此 `/tmp/../etc` 仍由 token 级 `..` 判据拒绝，`/tmp-link` 不匹配，临时目录内指向外部的 junction／symlink 仍由真实路径检查拒绝。Linux/macOS 不走该例外，文件工具的 workspace 根与 `SandboxConfig` 均不改变。

代价：Windows Bash 获得用户临时目录这一处工作区外读写能力；普通交互仍有审批，`autoApprove` 明确选择不询问。映射依赖 Git for Windows 的 `/tmp` → Windows 用户临时目录约定，不探测任意 MSYS 挂载表，也不扩展 `/var/tmp` 或其他 POSIX 根。命令闸门仍是粗形状策略而非操作系统隔离。

### D-20 大工具结果的尾部窗口（NX-33）

当通用结果超过 `maxPreviewBytes`，或 Bash 单条流超过 `floor(maxPreviewBytes / 2)` 时，保留原有截断触发、纯前缀 `text` 长度和结果存储／回读契约。另从原文末尾取最多 `floor(maxPreviewBytes / 8)` 字节的 UTF-8 完整字符，预算取模块常量，不增加配置项。Bash 两条流分别计算，共用同一尾部预算。

只有前缀与尾部之间确有字节被省略时，才附加 `tail`、`omittedBytes = 原文字节数 - text 字节数 - tail 字节数`、`resumeOffset = text 字节数`；模型可从该偏移用 `read_tool_result` 回读中段。若原文只比触发阈值多一点、前缀与尾部已覆盖全文，则保留既有 `text`／`ref`／`previewTruncated` 形态，不附加新字段。`text`、默认预览大小、采集和预算阈值、`ref`、`storedBytes`、`truncated` 均不改变。

取舍：把首尾拼入同一个 `text` 会破坏纯前缀契约及 NX-08f 对照 B 的现有断言；仅保留前缀又让尾部的失败摘要需要额外一次回读。独立字段保持原契约，同时让尾部直接可见。请求载荷因此增大，旧对照 B 记录不再逐字对应现行构建；是否重跑实验另行预注册与授权。

## 默认参数与行为

### 请求规模与估算
- 输入目标 65,536 token；输出上限 16,384（reasoning + 正文）；输出预留最低 4,096。
- 容量余量 max(2,048, ceil(estimatedInputTokens × 10%))。输入估算不含此余量；input <= 输入目标，且 input + 输出预留 + 余量 <= 模型窗口。
- DeepSeek 官方 1M 窗口先保守配置为 1,000,000；自定义端点必须明确能力。显式 max_tokens，不沿用供应商默认大额度。
- 可替换估算器初值：Unicode ASCII/非 ASCII 字符分别按 0.3/1.0 token，加上角色、调用 ID、参数 JSON、reasoning、schema 等实际序列化内容；每消息 32、每请求 256 token 封装开销。这不是真实 tokenizer，代码/特殊符号可能有误差，来源标 estimated。
- 先移除最旧已结束完整任务/轮次；不截短当前 task 过程。当前集合无法容纳时 context_overflow；/continue 不自动扩大输入目标。
- 输出触及 length 时标 output_limit，不执行残缺调用；usage 结算后记录估算偏差。
- 估算偏差已实测（NX-08c，核验日期 2026-09-30，估算器 SHA-256 见 [CHANGES](CHANGES.md#nx-08c-输入估算误差实验)）：中文 +28%、英文 +40% 一致高估；代码与 JSON 不是一致安全，40 个样本中 4 个低估、最深 −22.5%，**超过容量余量的 10%**。因此输入目标 65,536 与容量余量都只按估算器口径成立，按真实 token 计会更宽松；反向地，单个请求仍可能超出估算判断。参数按估算器口径固定，不因本结论在真实调用开始前调整。

### 每段执行与续跑
- 模型请求 64 次，工具调用 128 次，主动时间 600,000ms，累计输入加输出 2,000,000 token。
- 主动时间包括组装、模型、工具和持久化；人工审批等待暂停，单次审批限 300,000ms。模型请求限 180,000ms，Bash 保留 30,000ms、Context7 保留 60,000ms，均受剩余主动时间约束。
- 最后一次模型请求若给出完整答案可完成；若继续要求工具，全部标 skipped 后停止，避免产生无法继续判断的副作用。其他批次按顺序执行至预算耗尽。
- 请求前预留输入、容量余量和输出；余额不足先降低输出上限，连最低预留也不足则 token_budget。最低预留不要求实际生成至少 4K。
- /continue 显式开启同 task 的新 run，默认追加相同额度；run 显示本段，task 持续累计次数/token/主动时间/续跑数。用户停留及审批等待另计，无隐藏任务总上限。
- completed 不继续；上下文配置未调整的 context_overflow 仍拒绝；取消后显式继续仍检查 unknown。unknown 副作用先核验，不自动重试。
- 64K/16K 控制工作集及单次生成；2M 限制重复发送的累计消耗。满 64 次请求不保证可用满，其他额度可能先触顶；不承诺严格费用上限。

### 持久化与 reset
- 默认 ~/.mini-dsh/sessions/<sessionId>/events.jsonl，可配置覆盖；记录规范化 workspace，恢复到其他目录不得直接执行。
- session 单写入者持锁，第二写入者失败；失效锁显式核验，不仅凭 PID 自动移除。核验入口是 `pnpm session:lock <sessionId>`（只读检视锁体、pid 探针与尾部状态），解除要 `--remove --token <检视输出里的 token>`——token 对不上即拒绝，pid 只作线索。
- 非流片段语义事件（请求/工具开始、结果、用量、终态、reset）串行追加并等待 sync，再调度后续操作；写入失败停止。新文件目录耐久性按平台核验，不承诺任意设备掉电保证。
- 流片段按 250ms 或 4KiB 合并追加，不逐 token sync；完成/中断追加状态并 sync。投影只用完整响应，不重复派生片段；崩溃可能丢失未写入尾部，明确标不完整。
- 尾部半条记录保护原文件并隔离后才能继续；中间损坏、缺序号、未知版本停止恢复，不静默跳过。
- reset 追加 session/reset，保留 sessionId、全局递增 seq 及文件；投影切换 epoch，旧任务不可继续；不物理删除日志。
- 保存 Harness 实际捕获内容；不自动解除 Bash 的 32 KiB 截断。日志不提交仓库，凭证不写事件；崩溃恢复不是文件系统快照。

## NX-07 有界工具决策
- read_file 默认 startLine=1、maxLines=200，输出最大 32 KiB；扫描最大 8 MiB，每次只读 8 KiB，单行超过输出上限明确失败，支持继续读取后续行。文件必须普通 UTF-8 文本；NUL/非法编码拒绝。
- glob/grep 默认 path='.'、offset=0、maxResults=200，最大输出 32 KiB；遍历最多 10000 条目，深度 64，单文件扫描 1 MiB、累计 8 MiB。流式目录遍历不跟随软链，默认忽略 .git/node_modules/dist，可 includeIgnored=true。分页 offset 为重新扫描后的匹配偏移，不承诺文件变化时稳定快照；超限返回原因和 nextOffset，无法越过扫描限额时提示缩小目录。
- 所有限额为正安全整数并可通过 files 配置调整；调用参数只可降低 maxLines/maxResults，不可扩大配置上限。
- 工具预览默认 16 KiB、结果采集最多 8 MiB、磁盘总额 64 MiB，均可配置。结果存储默认位于工作区 .mini-dsh/tool-results，随机 UUID 引用绑定 session，SHA-256 校验内容；无 session 时不创建引用而保留原运行时兼容。磁盘失败返回 ToolError，不静默丢失。容量耗尽明确失败，不自动删除历史。
- read_tool_result 以 UTF-8 字节偏移有界读取，返回 nextOffset/eof；偏移须落在字符边界。引用是数据，不是文件路径；没有同 session 或文件丢失/损坏时报错。回读工具本身不再次存储，释放插件移除其注册。
- Bash 保持审批、超时、退出码语义，改为采集最多 8 MiB（可配置），保留超限标记；失败日志也可引用。模型/JSONL 保存预览和引用，完整内容放在结果文件中，不修改历史事件或预算逻辑。

NX-07 集成补充：搜索也默认忽略 .mini-dsh；read/search 的 maxOutputBytes 限制正文/匹配载荷，不包含有界元数据与 JSON 格式包装。存储另设 maxFiles=1000，额度检查在单 ToolResultStore 实例内串行；多进程共享目录没有全局配额锁。CLI 默认注入结果投影，无 session 的底层调用保持兼容；回读上限默认 16 KiB。文件/Bash 采集有限与完整请求预算分别生效。

## NX-08 评测批次上限（预注册）

真实模型调用开始前固定下列参数；固定后只能整体重跑，不得为提高通过率单独调整某一臂或某次重复。调整时须在报告中说明改动与理由。

不变量（全部运行共用）：

- 模型固定为单一模型，记录具体名称与版本；两臂之间以及 Bash、文件、结果存储、prompt 等非上下文参数保持一致。
- 各臂一致的单次 run 预算：模型请求 32 次、工具调用 64 次、主动时间 300,000ms、累计 2,000,000 token。**这一组是「每个阶段一份」**：多阶段 fixture 的每个阶段都是一次 `agent.send()`，各自新建 `RunState`、counters 归零，因此整条序列的上界是「阶段数 × 这组值」（实测确认见下）。
- 其中请求数 32 是**约束**：两臂获得相同工作量，被比较的才是上下文策略而不是预算。2,000,000 token 是**兜底**，正常 fixture 任务不应触及，否则"预算耗尽"会混进所测的 token 用量。
- 该组值低于 CLI 默认的 64/128/600,000ms/2,000,000 token；CLI 默认面向通用使用，对小型 fixture 过宽，会掩盖上下文策略差异。
- 上列四项是**覆盖值**，其余参数取「默认参数与行为」的文档值；评测侧由 `evalPolicy = {...CLI_BUDGET, ...singleRunBudget}` 组装（NX-08d0-1），模型窗口按端点显式声明，官方端点取 1,000,000。只传这四项会让投影失去输入目标与窗口：`ContextBudgetRuntime` 对两者均未配置时恒判可容纳，裁剪与 `context_overflow` 全部失效。
- 入口按**阶段**选择批次（NX-08e2-2）：`scripts/eval-screening.ts` 接受 `--phase`（默认 `screening`），默认清单取该阶段的注册表而非全部 fixture，`--tasks` 只能在其内部取子集（跨阶段取任务会让计划任务数超过该阶段上限）。`--plan-only` 在建立目录、发出请求之前打印计划、上限、模型、输入目标与证据目录，供人在花钱前核对——输入目标就是两臂的差异所在，预演里看得见。
- 对照有效性条件（2026-09-30 修正）：两臂要产生差异必须**同时**满足两个条件——**会话组成**上存在已结束且可裁剪的旧任务，**规模**上这些旧任务的累计估算输入足以让 `fits` 为假。原表述只写了规模条件（「历史超过输入目标 65,536」），据此推出的「构造更大的任务」不成立，理由如下。
- 裁剪的触发条件是会话组成，不是任务规模。`ContextBudgetRuntime.groupHistory` 按 `taskId` 分组，只有 `taskId === currentTaskId` 的组被标 `protected`（`src/core/context-runtime.ts:29`），`project()` 的循环只移除 `!protected && complete` 的组（同文件 `:68-70`）。而新的 `agent.send()` 一律分配新 `taskId`，只有 `/continue` 才复用旧 taskId（`src/core/session-runtime.ts:135`）。因此**当前 task 无论多大都不会被裁剪，`/continue` 的续跑段同样恒受保护**（R-12 与 `test/continue.test.ts` 的「完整当前过程跨续跑保留」）。能够被裁剪的只有**同一会话中更早结束的其它任务**。
- 由此，`scripts/eval-fixture.ts` 现有驱动每个 fixture 只建一个 session、只发一次 `agent.send()`（`:42-50`），会话里永远只有一个 task，`removedTaskIds` 恒为空是**结构性必然**，与任务规模无关。筛查跑 12 个 fixture 全部 `removedTaskIds` 为空，不能据此推断任务「太小」。
- 因此 NX-08e 的前置是让评测驱动产出**多任务会话**（同一 session 内多个 `taskId`），而不是放大单个任务。对照 A 采用同仓库、后阶段依赖前阶段产物的多阶段任务序列。（对照 B 不受此限制：有界工具输出改变的是当前 task 内部的历史规模，单任务下就会让一臂 `context_overflow`、另一臂完成，两臂可直接分辨。）
- 实测数值分列，不可混用：筛查跑 12 个 fixture 的最大估算输入为 17,220（`CHANGES.md` 的 NX-08d 节）；NX-08d0-3 的 `merge` 烟测在 9 次请求后达到 27,147（`CHANGES.md` 的 NX-08d0-3 节）。后者是单 fixture 重复两次烟测得到的数，不是 12 个 fixture 的最大值。
- 覆盖值重算（**已于 2026-10-01 完成，见下面的「按实测重预注册」**）：`phaseCaps` 的 `armA`/`armB` 原各 72 次运行按「12 任务 × 2 臂 × 3 次」算出。fixture 变成多阶段序列后 `runs`/`requests`/`tokens` 的口径与算术都重算，旧数值 72/2,400/45,000,000 与「全程 156 次」一并作废。

**阶段与臂的对应关系（2026-10-01 明确）**：`phaseCaps` 的两个对照阶段就是**对照 A 的两条臂**——`armA` 是「全历史」臂，`armB` 是「现有裁剪」臂。此前文档把 `armA`/`armB` 读作「对照 A 批次 / 对照 B 批次」，并据此把 156 = 12 + 72 + 72 写成「筛查 + 对照 A + 对照 B」；现在按运行期实际语义固定为前者。**对照 B 因此不再有对应的阶段与上限**：它有界工具输出的开关尚未设计，等 NX-08f 开跑前单独预注册，不得沿用本轮数字。

整批上限（运行器侧硬中止，按阶段独立计数；触顶即中止该阶段并报告，不记作任务失败）：

- 筛查 12 次运行：请求 400、token 8,000,000。
- 对照 A 两臂各 3 次运行（1 条多阶段序列 × 3 次重复 × 2 臂 = 6 次）：每臂请求 1,400、token 40,000,000。
- 整批 18 次运行：请求 3,200、token 88,000,000。

**按实测重预注册（NX-08e2-6，2026-10-01；NX-08e2-4 随序列扩到十四阶段再重算一次）**。旧算式「12 任务 × 2 臂 × 3 次」随 fixture 变成多阶段序列而作废——「一次运行」的含义从「一个单任务」变成「整条序列」。新数字的依据：

- 请求上限取**理论上界**：3 次 × 14 阶段 × 32 请求 = 1344，进位到 1,400。与筛查同口径（12 × 32 = 384 → 400）。取理论上界而不是实测是刻意的：请求数 32 是「两臂获得相同工作量」的约束，上限若比它更紧就会在中途掐断某一臂，让被比较的东西从上下文策略变成预算。6 阶段批次两臂各自只用了 100 / 125 请求，14 阶段诊断单次 132 请求，离上界都很远正是它该有的样子。
- token 上限取**实测的两倍余量** `3 × 2 × 单条`：14 阶段诊断实测单条 6,379,862 token（132 请求，`accepted=true`），`3 × 2 × 6,379,862 = 38,279,172`，进位到 40,000,000。
- **这条数值先按外推写过一版，被实测推翻，教训留在这里**：当时用 10 阶段的 2,639,688 加上 4 个「同量级」的受裁剪阶段外推得 3,884,608，据此定的上限是 24,000,000；实测 6,379,862，比外推高 64%。原因是 **token 由每阶段请求数驱动，不是阶段数线性外推**——14 阶段平均 9.4 请求/阶段（第 6、9、13 阶段分别用了 17、15、13 次），而 10 阶段那次只有 6.4。按外推值定的 24,000,000 对 3 次运行只剩 25% 余量，而 6 阶段批次的跑次间波动有 2.4 倍宽（0.82M～1.95M/run），那个上限正好会犯上一条明令禁止的错：在中途掐断某一臂。**外推的 token 数不能替代实测，尤其不能用来定硬中止阈值。**
- 单次 run 预算是每次运行的硬闸门（见下），整批上限是兜底；实测从未触及任何一处上限。按实测单条 6,379,862 估，6 次运行约 38M token，即每臂约 19M——落在 40,000,000 的一半以内。
- **样本量只有 1 条 fixture × 3 次重复**：`sequenceIds` 目前只有 `pipeline` 一条。这够看重复间波动的大致量级，不足以支撑「通过率差异」这类需要分母的结论，报告里必须如实写明。**加阶段买的是「处理真的生效」，不是统计功效**——这一点在 NX-08e2-3 被 n=6 否证之后已成文，见下。
- **结局有效性条件（NX-08g0，2026-10-01 补）**：除会话组成与规模之外，还有一条此前没写进预注册的条件——**结局必须能取到不同的值**。两处独立测量都取满值（NX-08d 12/12、NX-08e 6/6），以 `accepted` 为分子的统计量**方差为零、没有分辨力**。它与上一条的样本量是**两个独立的限制**：样本量小影响区间宽度，天花板上限让被估计的量本身失去取值。当前 fixture 测量的是「在有完整、即时、廉价 oracle 的条件下能否收敛」（公开且受保护的 `check.mjs`，十四阶段说明全都给出该命令），不是「能否独立产出正确实现」。**后续任何通过率型结论在打破天花板之前都不能写成「提升」，只能写成「链路可用」**；补救方案与成本排序见 CHANGES 的 NX-08g0 节。**方案 2 已由 NX-08h 执行**——新 fixture `blind` 去掉工作区里的公开 `check.mjs`，其仪器、可比性与判据见 [NX-08h 一节](#nx-08h-无公开检查变体blind)；本条件说的是「哪条结论不能写」，不因仪器更换而失效。**注意换连续指标救不了对照 A**：唯一有明显差异的 token 正是处理本身设定的量，属操纵检查而非结局。

token 上限的口径：筛查按每次运行 600,000 估算，约为预估实际用量（每 run 约 300,000）的两倍。整批上限与单次 run 预算相互独立，不能用单次预算替代：对照 A 每臂 3 次运行各自用满，按「14 阶段 × 2,000,000」计就是 84,000,000 token，高于该臂 40,000,000 的上限。

**两臂的差异只有一个参数（2026-10-01）**：R-21 要求两臂共用同一模型、prompt、初始状态、验收器与单次 run 预算，因此差异被压缩到**输入目标**——`armB` 取文档默认的 65,536（历史超出就移除最旧的完整任务），`armA` 取模型窗口（让「输入 ≤ 目标」恒成立，历史只受窗口容量约束）。实现见 `scripts/eval-runner.ts` 的 `armPolicy`，它同时拒绝「窗口不高于 armB 的目标」这种会把两臂悄悄对调的配置。输出预留只由 `maxTotalTokens`/`maxOutputTokens` 决定、与输入目标无关，所以两臂的差异确实只在裁剪上。注意「全历史」不是无限：输入 + 输出预留 + 容量余量仍须落在窗口内，越过是 `context_overflow` 而不是静默截断。

上列 18 次运行只归约 `screening`/`armA`/`armB` 三个**预注册对照阶段**（`batchPhases`）。诊断性质的单次烟测不改变这个数字的含义，因此单独登记，不并入 `batchCaps`。

诊断阶段 `sequence`（NX-08e2 的烟测，多阶段 fixture `pipeline`）：

- 1 次运行：请求 448、token 28,000,000。
- 数值取**逐阶段预算的理论上界**（14 阶段 × 每阶段 `singleRunBudget` 的 32 请求 / 2,000,000 token）。这不是「预期消耗」，而是「不可能超过」：`runPhase` 只在两次 fixture 之间检查累计值，该阶段计划里又只有 1 个 fixture，所以整批上限对它**本来就不构成中途制动**。既然拦不住任何花费，取更紧的值只会把一次跑完的烟测变成带 `aborted` 的退出码 1，凭空制造一个会被误读成失败的结论。**上限必须跟着阶段数走**：留在旧值上，新的理论上界就会越过去，把一次正常的烟测记成 aborted——`test/eval-runner.test.ts` 现在把这条上限与 fixture 的阶段数逐字钉在一起。
- 因此该阶段真正的成本闸门是**每阶段的 `singleRunBudget`**：**单次 run 预算按阶段各计一份**（每个阶段一次 `agent.send()` → `beginRun` 新建 `RunState`、counters 归零），整条序列的上界即 14 × 32 请求、14 × 2,000,000 token。
- **`max_steps` 是这一步最需要警惕的伪信号**：某阶段用满 32 次请求会以 `max_steps` 停止并被如实记录，后续阶段拿到全新的 32 次额度继续跑。被截断的阶段里模型没做完，它的历史规模也就不是「模型自然需要多大」，不能用来判断「需要几个阶段才越过 65,536」——报告必须把这类阶段单列。

单次预算与整批上限的分工：单次预算由 Agent 循环在 run 内强制，触顶只停止该次 run 并给出停止原因，该 run 仍计入阶段与用量；整批上限由运行器在每次 run 之前与之后检查阶段累计值，触顶中止整个阶段并报告。**已经开始的 run 不会被整批上限中途终止**，因此触顶时的超出量以单次 run 的用量为上界。开跑前的检查取“累计 ≥ 上限”即中止，使上限恰好等于计划数时不会误报中止（筛查 12 次运行对上 12 次上限即属此列）；跑完后的检查取“累计 > 上限”。实现见 `scripts/eval-runner.ts`。

货币不作为硬上限。费用/币种预算仍属"暂不纳入"（D-01）；估算器存在已知误差，缓存与 reasoning 计费口径尚未核验，给出精确金额上限会制造虚假精确性。仅作信息性上界：按 2026-09-30 核验的[价格页](https://api-docs.deepseek.com/quick_start/pricing/)，98,000,000 token 按输入 85%／输出 15%、无缓存命中、峰值价计算，deepseek-flash 约 43 美元、deepseek-v4-pro 约 168 美元，off-peak 折半。该数字只用于判断实验规模是否可接受，不是计费承诺；实际用量预期明显低于上界，因为多数 run 不会触顶。

缓存按无命中估算：上下文裁剪会移除最旧任务并改变消息序列前缀，不能假设前缀缓存收益。

## NX-08e0 阶段序列驱动契约

对照 A 要求会话中存在已结束且可裁剪的旧任务，因此 fixture 驱动的输入从「一个任务」扩为「一个任务序列」。契约如下，本步只固化驱动与布局，不新建多阶段 fixture。

- **两种布局互斥**：`test/fixtures/coding/<id>/TASK.md` 是单任务，`test/fixtures/coding/<id>/TASKS/*.md` 是按文件名排序的阶段序列（顺序由 `01-`/`02-` 这类前缀承载，不由目录项返回顺序承载）。同时存在两者直接报错：接受哪一种就决定了模型被要求做多少，而读者很难察觉，这正是「任务做大一点就能触发裁剪」那条错误判据的同一类陷阱。`TASKS/` 里没有 `.md` 同样报错，不静默退回单任务。读取逻辑见 `scripts/coding-fixtures.ts` 的 `readTaskSequence`。
- **同一 session 内按序下发**：驱动对每个阶段调用一次 `agent.send()`，每次分配新 `taskId`，于是先前结束的阶段成为可裁剪的旧任务——这是对照 A 能产生差异的前提。不用 `/continue` 串联阶段：它复用 `taskId`，所有 run 并进同一个受保护组，裁剪同样不会触发。
- **验收仍是终态一次判定**：`fixture.evaluate()` 检查的是工作区终态，不按阶段拆分，因此不新增阶段级验收契约。`RunOutcome.status` 取最后一个阶段的状态，`counters` 是各阶段之和，逐阶段的观测留在新增的 `tasks` 明细里，用于定位是哪个阶段把预算或上下文用光。
- **基础设施失败中止后续阶段**：非 `BudgetStop` 的异常记入 `error` 后不再下发下一阶段——会话或工作区已经不健康，继续跑只会把同一个失败重复记成多份，而每一份都会进入阶段累计用量。预算触顶不属于这一类，它由 run 状态承载并继续下一阶段。
- **上限口径**：`phaseCaps` 的 `runs` 仍按 fixture 运行次数计；`requests`/`tokens` 现在包含各阶段，写法不变但含义从「单任务」变成「整条序列」。因此上限数值必须在开跑对照 A 之前重新预注册，不能沿用 12 任务 × 2 臂 × 3 次的旧算术。
- **规模换算（NX-08e0-3 实测，2026-09-30）**：诊断探针 `docs/context-budget/nx08e-prune-probe.mjs` 在同一会话内按序下发 N 个阶段测得——固定开销（system + 工具 schema + 一条最小 user 消息）1,909 token；每阶段载荷 2,000／8,000／32,000 token 分别在**第 31／8／2 个阶段**触发裁剪。触发后进入「每新增一个阶段就丢掉最旧的一个」的滚动状态（2,000 那组在裁剪点输入停在 64,411 不再增长），这正是两臂开始分叉的位置。把某个阶段的真实历史规模代入即得所需阶段数：现有 fixture 的真实单任务峰值 17,220（筛查跑）与 27,147（`merge` 烟测）同量级的阶段约需 3～4 个才能越过 65,536。探针测的是协议与载荷开销，不是真实模型轨迹，最终阶段数以多阶段 fixture 的真实工具流量为准。

## NX-08e1 多阶段依赖 fixture：`pipeline`

e0 只固化了驱动与布局，没有 fixture 声明 `TASKS/`。`pipeline` 是第一个，也是对照 A 的仪器。

- **任务形态**：同仓库、后阶段依赖前阶段产物的**十四阶段**序列，实现在 `test/fixtures/coding/pipeline/`。01 解析声明文件（重复声明合并、外部依赖、带行号的格式错误）→ 02 拓扑排序（依赖在前，并列取首次出现位置最靠前者）→ 03 环检测（非平凡强连通分量与自环，从顺序中排除）→ 04 分批（批号 = 内部依赖最大批号 + 1）→ 05 渲染报告（`docs/SPEC.md` 逐字固定的文本格式）→ 06 增量对比（把 05 的格式反向解析回来与当前计划比较）→ 07 反向解析（把 05 的渲染读回计划对象，**并回头重构 06 去调用它**）→ 08 计划合并（渲染→解析→合并→渲染的闭环）→ 09 阻塞原因（消费 01 的 `records` 与 03 的 `cycles`，给 `planPipeline` 加 `blocked` 字段）→ 10 审计报告（逐字固定的格式）→ 11 审计反向解析（与 07 对 05 的关系同构）→ 12 传递依赖闭包 → 13 子计划（用闭包做向下封闭的筛选，再按 02～04、09 节重算而不是过滤——过滤出来的批次会跳号）→ 14 审计增量（组合 11 与 09 的 `blocked`，形状与 06 的 `diffPlan` 一致）。每个阶段实现一个模块，`src/pipeline.mjs` 作为编排在每个阶段被接长。
- **依赖怎么落地**：`check.mjs` 的公开检查按阶段累积（`node check.mjs 4` 会重跑第 1 到第 4 阶段的全部断言），且每个阶段的断言只使用该阶段应当已经具备的字段，因此同一个受保护的 `check.mjs` 对所有阶段都成立；从 02 起断言 `planPipeline` 的返回值，逼着每个阶段回头改 `src/pipeline.mjs` 并复用自己上一阶段写的模块。06 的反向解析是刻意的闭环：最后一阶段必须回到自己在 05 产出的格式约定上，而不是再挂一个孤立模块。`docs/SPEC.md` 承载全部接口契约，因此每个阶段都会被读到。
- **验收不变**：`fixture.evaluate()` 仍是工作区终态的一次判定，不新增阶段级验收契约（见上面的驱动契约）。`verify.mjs` 用与工作区示例不同的一组输入独立验收：重复声明、自环、三元环、外部依赖、批量并列、环成员的间接依赖者。
- **阶段数是唯一可调旋钮，但它调的是「受处理阶段数」而不是「触发点」**：取 6 的依据是 e0-3 的换算（同量级阶段约需 3～4 个越过 65,536，6 留出触发后的分叉空间）——**这条依据已被真实数据两次修正**。6 阶段的正式批次显示 3 次 armB 只有 2 次真正裁剪；10 阶段的诊断跑在第 6 个阶段越过、后 5 个阶段受处理，并给出关键读数：**越过阈值的绝对阶段号大致固定，与总阶段数无关**（历史规模随阶段号近似线性增长），因此加阶段不改变越界位置，只增加越界以后还剩几个受处理的阶段，受处理阶段数 ≈ 总数 − 5。14 阶段的取值就是按这条读数定的：低波动的那条轨迹也留得下 7 个以上受处理阶段——**该预测在 NX-08e 的正式批次里成立**（3 次 armB 的首次裁剪落在第 8/6/6 个阶段，受处理阶段 7/9/9）。若将来还要调，增减的仍是最后一个阶段及其模块（`TASKS/14-*.md`、`src/audit-delta.mjs`、`check.mjs` 与 `verify.mjs` 同步），前面的阶段不用重做——`TASKS/01`–`10` 在 10→14 那次扩展里一字未改，这正是「越界位置与总数无关」在代码上的体现。
- **这条旋钮买不到什么**：加阶段买到的是「处理真的生效」，**不是统计功效**。样本量仍是 1 条序列 × 3 次重复 × 2 臂、二值结局，NX-08g 的报告不得据此写提升比例。
- **注册表分三份**：`screeningIds`（12 个单任务 fixture，**冻结**——NX-08d 的 12/12 与 `phaseCaps.screening.runs` 都以它为准）、`sequenceIds`（阶段序列）、`fixtureIds`（两者之和，`pnpm fixtures:check` 用）。`pnpm eval:offline` 只跑筛查批次，否则 12 的上限会把第 13 个计划任务挤掉，旧基线随之作废。
- **阶段性结论（2026-09-30）**：`pipeline` 已走通 `pnpm fixtures:check`（初始 0/13、参考 13/13）与驱动端到端路径（6 个阶段各自新 `taskId`、逐阶段 `completed`、终态验收通过、`counters` 为各阶段之和）。但**模拟适配器流量下整个序列的估算输入峰值只有 13,614**（逐阶段 11,695 / 12,175 / 12,536 / 12,862 / 13,208 / 13,614，`removedTaskIds` 全为空），远低于 65,536：模拟适配器在第一个阶段就应用了全部参考改动，后续阶段只回一句话，这个数字不代表真实模型的轨迹。因此**本轮不能判断 6 个阶段是否足以触发裁剪**，真实触发点由 NX-08e2 的烟测测量，`phaseCaps` 与单次 run 预算在那之后重预注册。

## NX-08e2 烟测实测（2026-10-01）

`pnpm eval:sequence` 跑了一次真实模型序列（`deepseek/deepseek-v4-flash`，服务端回显 `deepseek-flash`），证据在 `.eval-evidence/sequence-full/`。这一节是 e1「阶段数是估算」那条的答案，也是 `phaseCaps` 重预注册的依据。

- **6 个阶段足够触发裁剪，触发点是第 4 个阶段**（其第 8 次投影越过输入目标 65,536 并丢掉最旧的阶段）。阶段 1–3 从未裁剪，阶段 4 之后进入「每新增一个阶段就丢掉更旧的一个」的滚动状态：阶段 5 从第 1 次投影起就丢，阶段 6 把前四个阶段全丢、只留自己（current task 恒受保护）。因此**阶段数不再需要调整**，e1 里「阶段数是唯一可调旋钮」暂时不动。
- 逐阶段峰值估算输入：13,757 / 23,951 / 42,592 / **63,710** / 65,496 / 63,741。整条序列 53 请求 / 56 工具 / 2,188,159 token（input 2,125,115 + output 63,044），主动时间约 293 秒。
- **没有被 `max_steps` 截断的阶段**：最高 15 次请求、77 万 token，都远低于每阶段 `singleRunBudget` 的 32 请求 / 2,000,000 token。e0-3 与预注册节提示的那个伪信号没有出现，所以这些历史规模是模型自然走出来的。
- **单次 run 预算按阶段各计一份这一点被实测确认**：6 个阶段各自一次 `agent.send()`、各自一份 32 请求 / 2,000,000 token，最大的一阶段（06）也只用了 15 次请求。32 这个「约束值」在这里不是绑定约束——它保证了对照 A 两臂拿到相同工作量，而不是把某一阶段掐断。
- **`estimatedInputTokens` 是裁剪后的值，读法要小心**：阶段 5/6 的「最后一次投影」反而低于峰值（62,699 / 52,025 与 65,496 / 63,741）。判断某一阶段自身长了多少要看 `maxEstimatedInputTokens` 与相邻阶段的增长。裁**剪前**的规模没有落盘，只能由相邻投影外推。
- **这次运行的终态验收是 `accepted=false`，但失败点不是功能**：验收钉了 SPEC 没有规定的错误措辞。处置与依据见 [CHANGES 的 NX-08e2-3](CHANGES.md#nx-08e2-3-pipeline-的真实模型烟测与结论) 与 NX-08e2-5，读数本身（裁剪触发点）不受影响。

## NX-08f 对照 B：工具输出有界性

**自变量是唯一的：工具输出是否有界。** 其余（模型、prompt、初始状态、验收器、单次 run 预算、**输入目标 65,536**）两臂完全一致。两臂都开「现有裁剪」，即 `armPolicy` 对它们都返回 `evalPolicy`。

**实现方式：同一插件的不同配置，而不是装 / 不装。** `src/plugins/tool-results.ts` 在 `apply()` 里无条件注册 `read_tool_result`（`:53-61`）；`tools.schemas()` 每次请求都把工具表交给模型，`token-estimator.ts:10` 又把它计入输入估算。装 / 不装会让两臂的 `tools` 数组相差一个条目——既改变模型看到的能力，也改变估算，被比较的就不只是有界性，违反 R-21 的「两臂共用同一 prompt 与工具」。因此两臂**都**装载该插件，只改 `maxPreviewBytes`：

- **有界臂**：走生产默认（`positiveLimit` 的 16 KiB 预览；bash 每条流截到 `maxPreviewBytes/2` = 8 KiB），超出部分落盘并返回 `ref`，模型可用 `read_tool_result` 分页回读。
- **无界臂**：`maxPreviewBytes` 抬到 `UNBOUNDED_PREVIEW_BYTES = 64 MiB`（`scripts/eval-fixture.ts`）。bash 单流采集上限 8 MiB、经 `JSON.stringify` 转义后最坏约翻倍，因此任何单条结果都装得下，不会走截断分支、也不产生 `ref`。这是 NX-07 之前的行为。

**开关的落点是 `runFixtureTask` 的第 5 个可选参数**（`ToolOutputMode`）。不传时不装载插件——screening / armA / armB / sequence 与全部离线用例的行为因此一字不变，历史基线不受污染。

**为什么对照 B 不需要多阶段序列。** 对照 A 要产生差异，会话里必须存在**已结束且可裁剪的旧任务**（`context-runtime.ts:29,68-74` 只移除 `!protected && complete` 的组），所以它必须用多阶段序列才能构造出可裁剪的历史。有界工具输出改变的是**当前 task 内部**的历史规模，而当前 task 恒 `protected`、无法被裁剪——单任务会话下无界臂就会 `context_overflow`、有界臂完成。**两臂的可测性因此不对称，这不是缺陷而是两种处理作用在不同位置的必然结果。**

**判别量是结构性的，不是通过率。** 对照 B 的分辨信号是 `context_overflow`（`agent-loop-runtime.ts:80`）这个事实，不需要两臂在 `accepted` 上分出高低——因此 NX-08g0 判定的「任务集天花板效应」不会让对照 B 失效。反之，**两臂的 token 差正是处理本身设定的量，只能作操纵检查，不得写成收益**。

**尚未预注册。** `phaseCaps` 的 `armA`/`armB` 已归属对照 A 的两条臂，对照 B 的两臂（`armC` 有界 / `armD` 无界）的阶段与整批上限留到 NX-08f-5，**且必须晚于 f-4b 的真实模型烟测**：NX-08e2 的教训是外推的 token 数被实测推翻（外推 3,884,608 / 实测 6,379,862，差 64%），预注册不得建立在没有实测支撑的外推上。样本量按用户选定为 **1 条 fixture × 6 次重复 × 2 臂**。

## NX-08h 无公开检查变体（`blind`）

**它针对的是 NX-08g0 定性的天花板效应。** 两处独立测量都取满值（NX-08d 筛查 12/12、NX-08e 对照 A 6/6），以 `accepted` 为分子的统计量**方差为零、没有分辨力**；机制之一是**公开且受保护的 `check.mjs` 就在工作区里、十四个阶段的说明全都给出 `node check.mjs N` 这个命令**，模型不必一次写对，只需能收敛到绿。NX-08g0 的方案 2 是「增设**无公开检查**变体：工作区不含 `check.mjs`，只能按 SPEC 自验」，攻击的正是这条机制。**它把被测的问题从「有完整、即时、廉价 oracle 时能否收敛」换成「能否按 SPEC 独立产出正确实现」。**

**仪器 `blind` 是 `pipeline` 的复制，只改三处**：删掉 `initial/check.mjs`；十四份 `TASKS/*.md` 的末句由「完成后运行 `node check.mjs N`」改为按 `docs/SPEC.md` 自验（其中 4 份的从句描述的是 `check.mjs` 的累积重跑机制，须重写而不是删命令）；`initial/docs/SPEC.md` 里两处提到 `check.mjs` 的句子改为只提独立验收。`TASKS/`、`initial/src/`、`reference/`、`verify.mjs` 的其余部分逐字来自 `pipeline`，阶段说明与 `pipeline` 对应文件**只差末段**。

**可比性**：模型、prompt、初始工作区、验收器、单次 run 预算（32 请求 / 64 工具 / 300000ms / 2,000,000 token）与**输入目标 65,536** 都与 NX-08e 的 `armB` 一致；**唯一差异是工作区不含公开 oracle**，且阶段说明相应改为按 SPEC 自验。因此这次读数与 NX-08e 的 6/6 直接可比。

**注册表与阶段**：`blind` 单独一份注册表 `blindIds`——并进 `sequenceIds` 会让 `repeatCount(1, 2)` 抛 `a phase scheduled for 1 runs cannot be split evenly across 2 fixtures`，并破坏「两臂用同一份任务集」这条对照 A 的前提。新阶段 `blind` 是**诊断烟测**，与 `sequence`／`smoke` 同口径：**不进 `batchPhases`**，`batchCaps` 因此保持 `{18, 3_200, 88_000_000}` 不变。

### 预注册（开跑前写死，之后不得改动）

- **规模**：1 个 fixture × 1 次运行。`phaseCaps.blind = { runs: 1, requests: 448, tokens: 28_000_000 }`。
- **上限的来历**：取**逐阶段预算的理论上界**（14 阶段 × 32 请求 = 448；14 阶段 × 2,000,000 token = 28,000,000），与 `sequence`／`smoke` 同口径。这是机械推导，**不是**对照批次按实测做的预注册——NX-08g0 要求「不得沿用本轮的 `phaseCaps` 数字」，指的是不得把 NX-08e 那套对照 A 的上限搬过来；`blind` 上的正式对照批次**尚未预注册**，其上限必须等这次烟测的实测之后另行确定与授权。
- **「天花板被打破」的判据（唯一）**：该次运行 `accepted === false`，**且同时**满足 `acceptance.exitCode === 1`、`acceptance.protectedFilesChanged` 为空、`acceptance.output` 含 `AssertionError`。三条缺一不可——`passed` 是三项合取（`coding-fixtures.ts:92-98`），缺了后两条的失败说明的多半是别的机器（模型改了受保护的规格，或验收环境本身出问题），不是「没有 oracle 就做不出来」。
- **「因其它原因被拒」**：`accepted === false` 但上面三条不同时满足（尤其 `protectedFilesChanged` 非空，或存在以 `max_steps` 结束的阶段）。这类结果**不计入判据**，也不得转写成能力结论。`max_steps` 是已知的伪信号：没有 oracle 之后模型可能在某阶段多花轮次，而这类阶段的历史规模不是模型自然需要的。
- **「未被打破」的判据（唯一）**：`accepted === true` 且没有阶段以 `max_steps` 结束。此时只可写「这一次没有失败」，**不得**写「无公开检查不影响结果」「模型不需要 oracle」，或任何比例、对比、提升。
- **无论结果如何**：不改 `blind/` 任何文件、不改 `pipeline/`、不改 `phaseCaps.blind`、不重跑。重跑必须先记录本次结果并取得新的授权。**继续调 fixture 直到出现预期分叉就是按结果挑仪器**（红线沿用 NX-08f-4c）。
- **必须如实报告**：逐阶段的 `status` 与请求／token、`protectedFilesChanged`、`acceptance.output` 原文（它是唯一能说明「哪条断言没写对」的证据）、是否出现 `max_steps`。**n=1 只作存在性证明**：一次 `accepted=false` 是「天花板不是普适的」的存在性证据；一次 `accepted=true` 什么也不证明。
- **不做方案 3**：本次只改一个因素（有无公开 oracle）。若这次仍取满值，抬难度（规格留冲突、跨多文件重构、不可逆步骤）是另一个需要单独立项的实验。

### 实测结果（2026-10-01 追记，**以上条款逐字未改**）

- **该次运行 `accepted === true`**（`acceptance.output` 逐字为 `acceptance passed: blind`、退出码 0、`protectedFilesChanged` 为空），零 `max_steps`，成本约 $1.43（off-peak 口径）。按上表**字面命中「未被打破」**：只可写「这一次没有失败」。
- **上表漏了一种情形，照实记在这里而不是回改判据**：「未被打破」那一行只防了 `max_steps`，而这次有 **4/14 个阶段以 `context_overflow` 结束**（第 6、7、13、14），每个留下 1 个未发出的投影。触发点是 `agent-loop-runtime.ts:80-81` 的**输入目标**合取项（`estimatedInputTokens > 65,536`），发生在裁剪之后——那四个阶段已经把能裁的旧任务裁到底（5／6／12／13 个），当前任务单独就超了；窗口是 1,000,000，与它无关。**这是一处已知的判据缺口，不是把结果归进「未打破」的理由。**
- **`blind` 上的正式对照批次仍未预注册**，其上限必须等新的实测之后另行确定；与 `armB` 的比较不在本次预注册内。
- 详细读数、机制与「不能支持什么」见 [CHANGES 的 NX-08h 节](CHANGES.md#nx-08h-打破任务集天花板方案-2无公开检查变体)。
