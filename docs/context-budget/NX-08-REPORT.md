# NX-08 真实模型评测报告

更新：2026-10-01（NX-08f 收尾）。本文件是 NX-08 三次真实模型实验的**读者面向报告**——合并 NX-08d 筛查跑、NX-08e 对照 A 与 NX-08f 对照 B 的结论。逐步的行为、提交与验收证据在 [CHANGES](CHANGES.md)，参数与预注册口径在 [PLAN 的评测批次上限](PLAN.md#nx-08-评测批次上限预注册)，执行状态在 [TASKS](TASKS.md) 与 [PROGRESS](../../PROGRESS.md)。

**范围**：只覆盖有独立验收口径的实验。NX-08c 的输入估算误差实验另见 [CHANGES 的 NX-08c 节](CHANGES.md#nx-08c-输入估算误差实验)，此处只引用其结论（对自然语言一致高估、对结构化工况不是一致安全），不重述数值。**NX-08f 对照 B 的仪器未成立**，它的价值是负面结果与机制解释，单列一节。

## 结论摘要

1. **链路可用，能力结论不可写。** 18 次真实运行零基础设施失败、零人工介入、零不可行项，Harness 能在这条链路上跑通并交付。但两处独立测量的通过率都取满值（筛查 12/12、对照 A 6/6），**方差为零**——不是「差异很小」，是**量不出来**。判据、机制与补救排序见 [NX-08g0](CHANGES.md#nx-08g0-任务集天花板效应定性边界与补救排序)。
2. **对照 A 的处理确实生效，但它省下的是上下文规模，不是步数或时间。** armB 三次的首次裁剪落在第 8/6/6 个阶段、受处理阶段 7/9/9（共 14），末阶段峰值估算输入 armA 150,228 vs armB 56,690（差 2.65 倍）；但两臂请求数只差 5.4%，墙钟 armA 18.7 vs armB 19.6 分钟。**token 少 45.4% 是操纵检查，不是效率提升。**
3. **两条独立的限制**：结局饱和（被估计的量失去取值）与样本量小（只有 1 条 fixture 序列，区间宽度无意义）。二者不可互相替代，见下文专节。
4. **对照 B 的仪器没有成立，结论是负面的。** 有界工具输出这个自变量在两次烟测里都没有被触发：模型两次都没有在破损状态下跑过会产生大输出的那份报告，峰值估算输入分别是输入目标的 51% 与 41%。**机制可解释**：给 agent 一个通用 shell，它就能把大数据在**工具进程里**降维成小摘要，不需要读进上下文。**这不是「有界工具输出无影响」的证据**，见「NX-08f 对照 B」一节。
5. **成本约 $5.01**（筛查 $0.15 + 对照 A $4.81 + 对照 B 两次烟测 $0.05，各自按当日适用的价格规则算），按价格页直接算，不引用不可复现的历史金额。

## 仪器与不变量

- **模型**：`deepseek/deepseek-v4-flash`，服务端回显 `model=deepseek-flash`（该名是 Flash 当前档位的旧标签）。端点 `https://api.deepseek.com`，窗口按 PLAN 保守配置 1,000,000。
- **两臂的差异只有一个参数**：`armB` 的输入目标取文档默认 65,536（历史超出就移除最旧的完整任务），`armA` 取模型窗口（「输入 ≤ 目标」恒成立）。实现见 `scripts/eval-runner.ts` 的 `armPolicy`，它同时拒绝「窗口不高于 armB 目标」这种会把两臂悄悄对调的配置。prompt、初始工作区、验收器与单次 run 预算两臂完全一致。
- **单次 run 预算，按阶段各计一份**：32 请求 / 64 工具 / 300,000ms / 2,000,000 token。每个阶段都是一次 `agent.send()`，各自新建 `RunState`、counters 归零，因此整条序列的上界是「阶段数 × 这组值」。请求数 32 是**约束**（两臂获得相同工作量，被比较的才是上下文策略）；2,000,000 token 是**兜底**。
- **整批上限**（运行器侧硬中止，按阶段独立计数）：筛查 400 请求 / 8,000,000 token；对照 A 每臂 1,400 请求 / 40,000,000 token。实测从未逼近。
- **验收判据**（两次实验同一套，取值按 fixture 而异）：退出码 0 + stdout 恰好等于该 fixture 的验收标记（`pipeline` 为 `acceptance passed: pipeline`）+ 受保护文件零改动。`pipeline` 的独立验收器 `verify.mjs` 在终态一次性加载并断言**全部 15 个阶段模块**（36 条断言），因此早期阶段的回归会体现在同一次终态判定里。

## NX-08d 筛查跑

12 个单任务 fixture 各跑 1 次，**原始分子/分母 12/12**，无拒绝、无不可行、无基础设施失败。

- 81 请求（上限 400 的 20.3%）/ 412,176 token（上限 8,000,000 的 5.2%），输入占 91.7%。
- 12 次全部 `completed`，没有一次触及 `context_overflow`、`token_budget`、`max_steps`、`timeout` 或 `output_limit`。
- **裁剪从未触发**：12 次 `removedTaskIds` 全为空，最大估算输入 17,220（`csv`）。这不是「任务太小」——裁剪只移除同一会话中更早结束的任务，而本批每个 fixture 只发一次 `send`，会话里只有一个 task，**为空是结构性必然**。规模是第二个条件，不是触发条件（依据见 [PLAN 的对照有效性条件](PLAN.md#nx-08-评测批次上限预注册)）。
- 任务间差异不小：最省的 `interface` 4 请求 / 13,315 token，最贵的 `csv` 10 请求 / 84,663 token，相差 6.4 倍。这是**任务间**差异，不是重复间波动。
- **只有 1 次重复，本批测不出重复间波动。**

| armB | 1 | 第 6 阶段 | 9/14 | 65,145 |

**3/3 触发，最低 7 个受处理阶段。** 作为对照，上一轮 6 阶段批次里 3 次 armB 有 **1 次完全没触发**（末阶段峰值 50,719，行为与 armA 完全相同，是一条不携带任何处理信息的对照-对照配对），另两次只剩 1～2 个受处理阶段。**加阶段这一步的目的由此达成。**

## NX-08f 对照 B：仪器未成立

对照 B 比较的是**有界工具输出 vs 无界工具输出**（NX-07 的 `tool-results` 投影与 `read_tool_result` 回读）。它与对照 A 的结构差别在于：有界性改变的是**当前 task 内部**的历史规模，而当前 task 恒受保护、无法被裁剪，所以**单任务会话**下两臂就能分辨——不需要多阶段序列。离线装置（f-3）也证明确实如此：同一台仪器、同一份预算、同一段脚本化工具序列，有界臂峰值 8,703 token 且通过验收，无界臂峰值 343,813 token 并在报告进入历史后的下一个投影 `context_overflow`，**相差 39.5 倍**。

**但真实模型下这条分叉没有出现。** 两次烟测（各 1 次运行，无界臂）：

| | 第一次 | 第二次（修掉第一处泄露后重跑） |
| --- | --- | --- |
| 策略 | `read_file` 分块抽样数据集 | **6 次 `node -e` 自写探针** |
| 结局 | `completed` / accepted | `completed` / accepted |
| 请求 / 工具 | 7 / 12 | 13 / 23 |
| token | 138,931 | 165,626 |
| **峰值估算输入** | **33,507（目标的 51%）** | **26,791（目标的 41%）** |
| **最大单条工具结果** | 32,832 字节（撞 `read_file` 上限） | **4,843 字节** |
| 在破损状态下跑过那份大输出命令 | **否** | **否** |

仪器是一台单任务 fixture：公开的 `check.mjs` 只有一条断言、失败输出指不出任何字段，而受保护的 `report.mjs` 会打印约 745 KB（≈223,573 估算 token，输入目标的 **3.41 倍**）的逐条不一致明细。**两次运行里模型都没有在破损状态下跑过它**——唯一跑到时都已改完代码，输出只剩 `SUMMARY 0`，其中一次还写成 `node report.mjs | tail -5`。

### 机制：通用 shell 让 agent 不必把大输出读进上下文

两次运行指向同一件事，而且它与模型个性无关，是**这个 Harness 构型**的可测后果：

- **agent 可以让自己写的小程序去消费大数据。** 第二次运行里，模型写的是 `node -e "const recs = readFileSync('data/records.jsonl') …"`——数据集在**工具子进程里**被读、被聚合，只有几 KB 的摘要回到上下文。第一次运行里的 `read_file` 分块、`wc -l && head -20`、`report.mjs | tail -5` 都是同一件事的不同写法。
- **因此「有界工具输出」买到的是另一类情形的保险**：agent **必须逐字理解内容、无法对它做计算**时的那一类。NX-07 的设计没有错，它防的是那一类失控；本次测的是「agent 会不会任由大输出进入上下文」，答案是**在这台仪器上不会**。
- **这条解释是可检验的**：要让它失效，任务内容必须**无法被脚本降维**——例如必须逐字读懂的长文档、或只有读过才能判断的语义内容。那意味着**换一类任务**，不是继续调现有的 `audit`。

### 两次运行里各修掉的一处仪器缺陷

两次烟测本身没有回答对照 B 的问题，但它们**发现并修掉了仪器自己的一处泄露**，这是可复用的：

- 第一次运行后确认的报告生成器源码里有一个 `RULES` 映射，把三条规范形式写成了可读的中文句子（1,404 字节的文件）。**读一遍源码等价于跑一遍报告**，报告的最大输出于是成了纯装饰。修法是让报告只打印「原始记录 / 当前的规整结果 / 规范值」三元组，规则只能从三者的对照里自己读出来。
- **修掉之后结局没变**：第二次运行中，模型在改写后的 `normalize.mjs` 里留下注释「规范形式（**由数据集的 expected 值反推得到**）」——它走的是**第二处**路径（数据集每行自带期望值，抽样即可反推规则）。这符合「一次只改一个因素」的读法：修掉的确实是真泄露，但它不是模型走的那条。
- **第二处泄露**（数据集自带金标值）没有继续修。理由见下。

### 为什么在这里停

- **继续改 fixture 直到出现预期的分叉，就是按结果挑仪器**——与 NX-08e2 那次「外推值被实测推翻」的教训同源。两次运行都在同一侧，且机制已可解释，再改下去买到的是仪器而不是知识。
- **n=2 且两次同侧，不足以写成「有界工具输出无影响」**，也不足以写成「模型总是收窄」。能写的是：**在这条链路上、这台仪器上、这个模型下，两次运行的机制解释一致**。
- **对照 B 因此没有进入正式批次**：`armC`/`armD` 的阶段与整批上限从未预注册，f-5/f-6 未开跑，也没有消耗对照级的预算。这一支的成本是两次烟测共约 **$0.05**。

## 两条独立的限制

报告必须把这两条分开写，它们不能用同一个理由解释，也不能互相抵消。

**限制一：结局饱和（方差为零）。** 以 `accepted` 为分子的任何统计量在两次实验里都没有可用的变异——筛查 12/12、对照 A 6/6，两臂都取满值。**没有失败可解释，量不出差异**。这与「差异很小」是两回事：差异很小仍可估计，饱和则是**被估计的量本身失去了取值**。机制是这份 fixture 把公开且受保护的 `check.mjs` 放在工作区里、十四个阶段的说明全都以「完成后运行 `node check.mjs N`」结尾，模型因此不必一次写对、只需能收敛到绿——它确实是这么做的（6 次运行跑了 151 次验证、118 次 `check.mjs`、96 次自写 `node -e` 探针；探针口径为「命令中含 `node -e` 的 bash 调用」，因此把探针接在 `check.mjs N &&` 之后的复合命令两处都计），而且收敛全部发生在同一阶段内，预算从未成为约束（零 `max_steps`，单阶段最高 14/32 请求、1,355,463/2,000,000 token）。判据、三条机制与五个补救方案的成本排序见 [NX-08g0](CHANGES.md#nx-08g0-任务集天花板效应定性边界与补救排序)。

**限制二：样本量小。** `sequenceIds` 只有 `pipeline` 一条，样本量是 1 条序列 × 3 次重复 × 2 臂。它影响的是**估计的区间宽度**——即便结局不饱和，这个规模也只够看波动的大致量级，不足以支撑需要分母的结论，更不能宣称统计显著性。

**两者不可互相替代**：样本量小可以靠多跑几条序列缓解（要花钱、要新预注册）；天花板效应不行——**加阶段买的是「处理真的生效」，不是统计功效**，这一点已由 6 阶段批次被 n=1 结论否证的历史印证过（见「失败案例」）。打破天花板要改 fixture 契约（NX-08h），且需要一次付费跑才能知道它是否真的产生失败。

**换连续指标救不了对照 A**：唯一有明显差异的连续指标是 token，而 token 正是处理本身设定的量，属操纵检查而非结局。**当处理的定义直接改变某个指标时，那个指标就不能再当结局。** 换指标只在「处理不直接作用于该指标」时才可行——修复次数勉强算一个，但 n=3 撑不住。

## 失败案例

两次实验的**运行级失败都是 0**——没有拒绝、没有不可行、没有基础设施失败、没有 `max_steps`。可报告的是三件比运行失败更小、但更有信息量的事。

**一、编辑失败：全是 Harness 的写入保护触发，不是模型写出坏代码。**

| | 筛查跑 | 对照 A |
| --- | --- | --- |
| 编辑变更 | 17 | 150（armA 70 / armB 80） |
| 编辑失败 | **2**（11.8%） | **6**（4.0%） |
| 原因 | 2 次 `oldText not found` | 5 次 `file conflict: expected <hash>, found <hash>` + 1 次 `oldText not found` |

一个反常读数需要解释：**筛查跑的失败率（11.8%）高于对照 A（4.0%）**，与「任务更难所以更容易出错」的直觉相反。原因是**分母不同**——筛查每个 fixture 只改一两处（17 次编辑 / 12 个任务），两处失败又集中在同一个 fixture（`pagination`，大日志定位那一项）：模型两次 `edit_file` 都因工作区文件是 CRLF、字面量匹配失败而被挡回，第三次改用 `write_file` 成功。对照 A 每条序列有 150 次编辑机会，失败率自然被摊薄。**两个数字不可直接比较**，n 也都很小。

六次 `file conflict` 是乐观并发保护（编辑基于过期的读），异常信息里「read again before editing」的提示是准确的；`oldText not found` 的提示「read the exact text including line endings」同样准确。**模型每次都当场恢复**，没有一次把失败带到下一阶段。

**二、修复迭代：真失败 5 次，全部修复，且集中在同一个阶段。**

「非零退出的验证」在对照 A 全批有 9 次，直接用它会高估。按**断言失败的阶段号与当前阶段号的关系**拆开：

| 分类 | 判据 | 对照 A |
| --- | --- | --- |
| 探针 | 命令不是 `check.mjs`，是模型自写的 `node -e` | 1 |
| 预期失败 | 断言失败的阶段 > 当前阶段（跑了后面的检查） | 3 |
| **真失败** | 断言失败的阶段 **=** 当前阶段 | **5** |

真失败 5 次全部随后再次编辑并转绿（5/5），随后的编辑合计 8 个。**5 次里 4 次落在第 6 阶段**（`src/delta.mjs`，把第 5 阶段渲染出的文本反解回「模块名 → 批号」），而 `TASKS/06-delta.md` 正好明文预警过那个坑——**被预告的陷阱仍然绊倒了 3/6 次运行**，说明它是真实的（尽管不大的）难点。**这是 fixture 的难度热点，不是处理效应**：armA 也命中过同一阶段，真失败在 n=3 下的 1 对 4 分不出处理效应与噪声。

筛查跑的真失败为 **0**——那一次非零退出的验证是模型自写探针的失败（`check.mjs` 已经打印 `public checks passed`，同一条 `&&` 链里随后自写的探针报错），属上表的「探针」一类。

**三、仪器结论被否证，这是本批次最值得留下的一条。**

NX-08e2-3 基于 **n=1** 的烟测判定「6 个阶段足够触发裁剪，e2-4 无需执行」。同一天的对照 A 实测在 n=6 下把这条否证了：3 次 armB 里只有 2 次真正裁剪，第三次的末阶段峰值 50,719 从未触及 65,536。**n=1 的那次恰好是偏高的轨迹**，它的读数不能外推到重复间。修法是把序列由 6 阶段扩到 10、再扩到 14。同一批还有一次同类错误：token 上限先按「阶段数线性外推」写成 24,000,000（外推得单条 3,884,608），实测单条 6,379,862，比外推高 64%——**外推的 token 数不能替代实测，尤其不能用来定硬中止阈值**。

另有两次更早的、与评测数据无关的 Harness 缺陷由筛查跑暴露并已修复：沙箱命令闸门把内联脚本里的 `//` 判成绝对路径逃逸、把 URL 文本判成出网请求（NX-17）。模型自行改用其他命令后仍通过验收，损失限于一次请求。

## 成本

按 PLAN 已写明的算法（价格页 2026-09-30 版；`deepseek-flash` 输入 cache-miss、输出；**假设无缓存命中**，这是保守方向），**每个批次按它自己时间窗适用的规则**算：

| 批次 | 时间窗 | 适用规则 | 成本 |
| --- | --- | --- | --- |
| NX-08d 筛查跑 | 2026-09-30 周三 07:00 UTC | peak | **$0.15**（off-peak 口径约 $0.08） |
| NX-08e 对照 A | 2026-10-01 02:37–03:05 UTC | 国庆法定假日，**不计 peak** | **$4.81**（若按 peak 则 $9.61） |
| NX-08f 对照 B 两次烟测 | 2026-10-01，国庆法定假日 | 不计 peak | **$0.05**（第一次 139k token 约 $0.02、第二次 166k 约 $0.03） |
| 合计 | | | 约 **$5.01**；全按 peak 为 $9.81 |

两行说明为什么对照 B 的数字比另外两批小三个量级：它**只跑到烟测就被判仪器未成立**，从未进入正式批次（`armC`/`armD` 的上限从未预注册）。这不是省下来的钱，是**这一支没有走到能花钱的那一步**。

off-peak 输入 $0.15/M、输出 $0.60/M；peak 输入 $0.30/M、输出 $1.20/M。对照 A 的时间窗落在 peak 区间（01:00–04:00 UTC）之内，但价格页写明中国法定假日不计 peak，2026-10-01 为国庆，故按 off-peak。**这一判断依赖假期规则而非代码，两个数都列出。**

两点必须随成本一起写：

- **缓存命中未记录**：事件流里没有 cache 字段，成本一律按无缓存命中计，真实账单应不高于此。
- **不引用不可复现的历史金额**。本轮一度拿 `PROGRESS` 里「6 阶段批次约 $4」反推 $/M 费率，把本批报高约 2～3 倍；那个历史金额本身按价格页重算只有 $2.53，**拿一个不可复现的数当基准去外推**，正是同一次工作里刚写进口径清单的那条毛病。以后报价一律用价格页直接算。

对照 A 的实际用量（两臂合计 30,699,056 token）低于它自己的整批上限（两臂合计 80,000,000）——余量仍在，但只剩约 2 倍；筛查跑的 412,176 token 对 8,000,000 则接近 20 倍。两处的共同点是**没有任何一次 run 逼近单次预算，上限从未成为约束**：**上限是兜底，不是预期消耗**。

## 结论边界

**可以写的（Harness 行为与链路可用性）：**

- 真实模型能在这条 Harness 链路上跑通并交付，两次实验 18 次运行零基础设施失败、零人工介入。
- 上下文裁剪确实生效，且两臂的分叉是结构性的：要触发它需要**会话组成**（存在已结束的旧任务）+ **规模**（累计估算输入让 `fits` 为假）两个条件同时满足，单任务会话无论多大都不会触发。
- 预算与整批上限从未成为约束：没有任何一次 run 触及单次预算；对照 A 的 token 用量约为该阶段上限的一半（余量 2 倍），筛查跑约 5.2%（余量 19 倍）。余量大小两处不同，但「从未触顶」这一结论一致。
- 编辑工具的写保护对 CRLF 工作区会把 `edit_file` 挡回 `write_file`，这是可复现的工具级行为，与模型能力无关。
- usage 全部来自 provider，估算回退一次都没发生。
- **有界工具输出这个开关本身是可用的、且离线可分辨**：同一台仪器、同一份预算、同一段脚本化工具序列下，有界臂峰值 8,703 token 并通过验收，无界臂峰值 343,813 token 并 `context_overflow`（39.5 倍）。这条是 **Harness 行为**，不是模型行为。
- **在两次真实运行里，模型都主动把大数据降维成了小摘要**（`read_file` 分块、`wc -l && head`、`node -e` 自写探针、`report.mjs | tail -5`），因此**对照 B 的自变量从未被触发**。这是关于**这条链路上 agent 行为**的观察，n=2。

**不能写的（真实模型能力）：**

- 任何通过率形式的结论，任何提升比例，任何「哪条臂更好」的判断——见「两条独立的限制」。
- 把 12/12 或 6/6 外推到长任务、大仓库、无公开检查的真实场景——公开且受保护的 `check.mjs` 这条机制在那些场景里不成立。
- 把「token 少 45.4%」读成效率提升——请求数与时长大致持平，省下的是上下文规模。
- 把「armB 真失败 4 次 vs armA 1 次」读成裁剪导致质量下降——n=3，且 4 次里 3 次挤在同一阶段、armA 也命中过该阶段。
- **把「对照 B 未观测到处理生效」读成「有界工具输出没有价值」**——那是仪器没测到，不是处理无效；两次运行、两次同侧，且机制已可解释。要重测需要换一类**无法被脚本降维**的任务，那是新仪器、新契约，不是继续调 `audit`。

**一句话**：本报告证明的是**这条链路在给定预算下可用、且上下文策略的差异能被这套仪器分辨出来**；它不证明模型在这档任务上的能力，也不证明裁剪对任务结果的影响，**更不证明有界工具输出有没有价值**——后者连自变量都没触发。前者要先打破任务集天花板（NX-08h），那需要改 fixture 契约、新的独立验收口径与一次新的付费授权。

## 证据位置与复现入口

- 原始证据（不入库）：`.eval-evidence/screening-full/`、`.eval-evidence/armA-14stage/`、`.eval-evidence/armB-14stage/`、`.eval-evidence/smoke-full/`（对照 B 第一次烟测）、`.eval-evidence/smoke2-full/`（修掉第一处泄露后的重跑）；被取代的中间批次保留在 `arm{A,B}-full/`（6 阶段）、`sequence-{10,14}stage/`、`*-pilot1/`。
- **对照 B 重跑换目录是刻意的**：`ensureWritable` 拒绝复用同一目录，而第一次的证据要保留——两次运行要能并排比对，才能看出「换了策略、避开的还是同一件事」。
- 每条 run 的 `runs.jsonl` 一行含状态、counters、验收结论与逐阶段明细；工具级统计（编辑失败率、修复迭代、探针数）**不在 `runs.jsonl` 里**——它的设计目标是逐阶段预算与裁剪观测——须从 `sessions/<fixture>/<sessionId>/events.jsonl` 现算，本报告的两个批次数字均按此口径得出。
- 付费入口 `pnpm eval:screening` / `pnpm eval:sequence` 每次调用都需要新的明确授权；证据目录每次运行只能用一次（`ensureWritable` 拒绝复用）。
- 离线可复现的部分：`pnpm fixtures:check`（初始 0/13、参考 13/13）、`pnpm eval:offline`（筛查批次 12/12）、`pnpm test`。三者都不调用付费模型。
