## 结论先行

“请求更少、token 更少、却耗时更长”不是一条因果，而是两个方向相反的聚合读数叠在一起：

1. **主动耗时几乎全是模型生成等待。** 旧/新两批的模型等待分别为 813,575 ms 与 867,171 ms（含摘要），占 899,287 / 959,303 ms 的 90.5% / 90.4%；工具合计只有 84,001 / 90,072 ms，投影与循环开销约 1.7～2.1 s。
2. **总 token 下降几乎全是输入 token；输出 token 反而上升。** 输入 3,937,718→3,647,881（-289,837），输出 127,701→143,322（**+15,621，+12.2%**）。延迟跟“生成了多少”走，不跟“读入了多少”走：逐请求的输出 token 与耗时 R²=0.973；逐 episode 的墙钟与输出 token 在两批合并后 R²=0.983（旧/新分侧 0.982/0.987）。每输出 token 的墙钟为 7.04→6.69 ms。
3. **三个变慢任务恰好是输出 token 上升最多的任务，其中 T04/R04 还多付了摘要。** F02/T04/R04 的输出分别 +5,518 / +15,798 / +7,043；T04 的摘要耗时 +44,427 ms，R04 +13,049 ms。两批摘要合计只多 2 次请求，却多花 45,004 ms，占净增 60,016 ms 的 **75%**。
4. **F02 的升幅集中在 repeat 1，且不是组件机制。** F02/1 从 15.1 s 变成 41.1 s：请求 6→8、输出 2,219→6,650、推理 455→3,784，其中两条请求各花 14.5 s 与 9.2 s；工具侧 +3.95 s 全部来自一条 `node smoke.mjs` 冷启动（3.6 s）。F02/0 反而从 24.9 s 降到 22.8 s。
5. **R04 两次重复方向相反。** R04/0 +88.3 s（首轮出现 29.1 s 摘要，请求 23→29，输出 9.4k→24.2k），R04/1 -51.9 s（摘要 16.1→0 s，输出 23.6k→15.8k）。单题聚合 +36.4 s 不能读成“优化让 R04 变慢”。
6. **重复回读、报告查询、验证命令都不是墙钟主因。** 全部 `read_file` 合计 0.05～0.17 s，`task_report` 合计 0.1～0.2 s；Bash 是唯一有量级的工具（T04/R04 各 11～17 s），其差异来自模型选择跑什么命令。报告正文（T04/0 7 次查询 111,673 字节）虽不花墙钟，却会进入上下文，间接推高压缩概率。

## 口径

- 墙钟 = 首条 `run/start` 到末条 `run/finish`；与 `runs.jsonl` 的 `activeDurationMs` 逐 episode 相差 0～0.1 s，两批聚合分别为 899,287 / 959,303 ms 对 898,977 / 958,913 ms（差 310 / 390 ms）。
- 模型等待 = `model/start → model/end`；摘要 = `model/start` 落在 `context/summary-start … context/summary-end` 之间的请求。
- 工具耗时 = `tool/start → tool/result`；`verification/*` 包含在 Bash 工具区间内。
- 投影/循环开销 = 墙钟 − 模型等待 − 工具耗时。
- provider 的 `outputTokens` 已包含 `reasoningTokens`；文中“输出”均指 `outputTokens`。
- 两批各 12 个 episode，串行、时间窗不同，供应商缓有可能跨会话共享。以下全是描述性读数，不是显著性、泛化或因果结论。

## 三个变慢任务的归因

### T04：摘要占一半以上，主请求本身并未变慢

- T04/0：主请求模型等待 **109.3→94.5 s（更快）**，工具 13.9→11.6 s（更少）；慢的是摘要 **9.9→40.4 s**（1→3 次）。第一次摘要把输入从 59,602 压到 41,096；随后新内容把上下文推回 53,655 和 56,808，各触发一次摘要。三次摘要的输出/推理分别为 3,523/1,950、2,145/310、2,831/760 token。
- 三次触发时，“已结束且非当前”的旧阶段任务分别占 **35,765 token**，而摘要只压当前 task；旧任务纹丝不动。
- T04/1：主请求 +9.3 s、输出 +6,747，摘要从 0 变成 13.9 s；工具只 +1.4 s。
- **T04 聚合 +82.5 s 中，44.4 s（54%）是摘要，其余是更长的生成。**

### R04：两次重复方向相反，单题聚合无归因价值

- R04/0：墙钟 67.1→155.4 s。首轮出现一次 29.1 s 的摘要（旧版该轮没有摘要），主请求等待 60.4→80.3 s，输出 9.4k→24.2k，Bash 6.1→16.1 s（4→8 条，其中一条目录遍历），请求 23→29。触发摘要时旧任务占 **41,127 token**，全部可裁。
- R04/1：墙钟 160.8→108.8 s；摘要 16.1→0 s，输出 23.6k→15.8k，请求 30→22。
- 两轮合计 +36.4 s，但方向完全由那一次首轮的长轨迹和一次摘要决定；不能从这 2 个样本推出组件效应。

### F02：纯生成长度与一次环境冷启动

- F02/0 反而更快（-2.1 s）。F02/1 的 8 次请求里，第 4、6 次各花 14.5 s、9.2 s，输出 2,840/2,325、推理 2,241/1,274；旧版同一题最长请求 6.1 s、输出 957。
- 工具 +3.95 s 来自 `node smoke.mjs` 在写入后首次执行（3.56 s）与紧随其后的验证命令（1.38 s）；旧版把两件事合成一条命令只花 0.93 s。这是进程冷启动/命令组织差异，不是预览、投影或报告查询。

## 可改点：摘要之后没有再裁旧任务

`project()` 只在投影**装不下**（输入超过 65,536）时才裁掉已结束的旧任务；压力线却在 `65,536 × 0.8 = 52,428`。于是：

1. 输入越过 52,428 时，旧任务仍在请求里；
2. 摘要只规划**当前 task 内部**的连续区间，旧任务不会被遮蔽；
3. 摘要后上下文降到 41k，但旧任务仍占 35～41k，几次主请求后又越线；
4. 同一段 run 里再付一次摘要。

T04/0 的三次摘要、R04/0 的 41,127 token 都落在这一模式上。设计文字写的是“免费的先做完，贵的才出手”，但压力路径没有先做裁剪。历史 [PLAN D-21](PLAN.md#d-21-当前任务历史的可回读压缩nx-34) 里“默认配置下 0.8 实际等价于裁剪救不了”这句话，只在**没有已完成旧任务**时成立；多阶段会话里它不成立。

### 已落地的修改：摘要后裁剪与持久化

`ContextBudgetRuntime.project()` 新增可选的 `pruneTargetTokens`；主循环在一次压力摘要**应用之后**用 `postCompactionTargetRatio × compactionBudget` 再投影一次，把已结束且非当前的任务免费裁掉。选择“摘要之后”而不是“摘要之前”是刻意的：NX-38 的 covenant 用例证明，先裁剪会让模型失去把旧阶段知识写进摘要的机会；摘要先发生，模型仍有机会带下去，随后再清掉旧任务，避免同一段 run 反复付费。

**只改当次投影不够。** 投影每一轮都从事件重建；如果裁剪只活在内存里，下一轮主请求、`/continue` 或重启恢复都会把旧任务原样带回来。裁剪因此写成 `context/prune` 事件：`trigger`、可选的 `summarySeq`、`targetTokens` 与 `removedTaskIds`。`project()` 读取日志里全部 `context/prune` 的并集，并在每一轮、每一段 run 与每次恢复中持久排除这些任务。事件本身也计入崩溃折叠，避免停在 prune 与随后的投影之间时状态不一致。

**原始事件一条不删。** 被裁掉的旧阶段仍在 `events.jsonl` 里，`read_history` 仍可按 seq 逐字回读；摘要正文也照常保留。裁剪是投影决定，不是删除，也不是改写。`session/reset` 之后 `visibleEvents` 的切片仍按既有边界生效；旧日志没有 `context/prune`，行为与之前逐字相同。

裁剪决定在摘要后的预算检查**之前**落盘：即使这次摘要正好用掉最后一次请求额度，后续 `/continue` 或恢复出的 run 也继承“这些旧任务不再进入投影”。

行为边界：

- 只有存在“已结束且非当前”的任务时才有变化；单任务会话与显式 `/compact` 不变。
- 摘要被拒绝或失败时不裁剪；只有 applied 之后才写 `context/prune`。
- 摘要后仍高于目标线或减少不足 5% 时，原有的 `context-pressure-suppressed` 仍会记录。
- 摘要是**有条件**的真实 provider 调用；本次没有为新行为发请求，也没有改写 NX-50 结果。

按已记录的轨迹做一个**反事实**（不是实测）：T04/0 第一次摘要后的 41,096 中约 35,765 来自旧任务，裁掉后约 5.3k；后续两次摘要分别由 53,655、56,808 触发，在裁掉旧任务后对应约 17.9k、21.0k，均低于压力线。因此那两次摘要（9.2 s + 12.6 s）在轨迹不变的前提下本可避免；R04/0 的 29.1 s 摘要仍会发生，因为它在第一次摘要前就已越线。把这两点相加，净增 60.0 s 中约 21.9 s 是摘要重复，剩余主要是输出 token 与模型采样长度。真实收益必须用新批次测，不能把反事实当结果。

持久化不改变上面的反事实读数：它保证的是首次裁剪后旧任务不会在下一轮、`/continue` 或恢复时回来。回归用例见 `test/compaction-trigger.test.ts` 的两条：一条钉住目标案例确实裁掉旧任务，另一条钉住后续轮次、`/continue`、重启恢复都不带回它们，且 `read_history` 仍读得到旧阶段原文。

**2026-10-25 的 24 条真实对照没有复现这段反事实。** `prune-on` 摘要 3→7、摘要耗时 43.2→105.4 s、主动耗时 +37.7%、输出 token +48.4%；可靠完成 11→10、产物验收 12→12。裁剪确实发生，但模型在裁剪后的轨迹上生成了更多输出，不能按“轨迹不变”的反事实推算收益。完整读数与逐题配对见 [NX-51 24 条结果](NX-51-PRUNE-RESULT.md)；按预注册规则，该行为已改为显式 opt-in 并默认关闭。

## 不是本次诊断能回答的问题

- **三项组件各自的贡献**：NX-50 只验证组合门槛。要归因，需要按组件构建 leave-one-out 版本，在同一模型/任务/预算下重跑；设计见 [NX-51 组件消融](NX-51-COMPONENT-ABLATION.md)，付费执行需单独授权。
- **采样方差与组件效应的分界**：2 次重复不足以区分。输出 token 的逐请求离散度很大（同一题最长请求可差 3 倍），正式批次需要更多重复或预注册的输出长度协变量。
- **摘要质量**：本次只能测摘要的耗时与 token，不能判断模型摘要内容是否足够好；那需要独立验收与人工/脚本审阅。
