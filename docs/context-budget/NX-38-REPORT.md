# NX-38 真实模型评测报告：两批四次开跑

更新：2026-10-14。本文件是 NX-38 两批四次真实模型开跑的**读者面向报告**。判据、四类结局与反 p-hacking 条款在开跑前写死于 [PLAN 的「预注册：两批」](PLAN.md#预注册两批开跑前写死)；把四条臂接进评测入口的施工与离线判定在 [TASKS 的 NX-38 表](TASKS.md#nx-38-区分度的获取设计零付费)与 [CHANGES 的 NX-38-4a 节](CHANGES.md#nx-38-4a-四阶段接入与离线判定)；执行状态在 [PROGRESS](../../PROGRESS.md)。

**本报告按预注册的要求分两段写，且不写任何比例或提升**：`n=3` 只作存在性证据与波动幅度，不作比率。两批的结论**不可互相解释**——批次 A 问「载体被拿走之后还守不守得住」，批次 B 问「模型会不会把口径带进自己写的摘要」。

## 结论摘要

1. **批次 A 的层 A 成立，判定 `ceiling-broken`。** `ledgerA2` 的每一次运行都裁掉了第 0 阶段的任务组，两臂的处理量区间不重叠；两臂的结局取到两个不同的值。**这只说明这台装置有能力分辨「裁」与「不裁」**——它不说明裁剪有害，也不含任何方向或幅度。
2. **批次 B 的层 A 不成立，按预注册不进层 B，判定 `instrument-not-established`。** `ledgerB1` 的主动压缩计数为 0：自变量从未被触发。机制见「批次 B」一节。
3. **两批各自回答一个问题，B 没有回答它的那个。** 把 A 的结局与 B 的仪器读数并排读，就是把两批各自没测的东西读进来。
4. **成本约 $1.30**（peak 口径；off-peak 约 $0.65），按价格页直接算，不引用不可复现的历史金额。

## 实验范围与不可行项

四条臂共用同一 fixture `ledger`（4 个阶段，`perFixture` 指纹 `e1b3d89063b953e2b3123ebb4d7239032891a5d6c87360941de1003c70876d5f`）、同一模型、同一 prompt、同一验收器与同一单次 run 预算 `evalPolicy`，差异**只由 `ledgerPolicy` 的一个字段承担**。

| 臂 | 组 | 自变量 | 运行数 | 层 A | 层 B | 证据目录 |
| --- | --- | --- | ---: | --- | --- | --- |
| `ledgerA1` | A | 不裁剪（目标 = 窗口） | 3 | — | — | `.eval-evidence/ledgerA1-full/` |
| `ledgerA2` | A | 裁剪（目标 = 22,791） | 3 | **成立** | **`ceiling-broken`** | `.eval-evidence/ledgerA2-full/` |
| `ledgerB1` | B | 生产默认（主动压缩在 52,428 触发） | 3 | **不成立** | **`instrument-not-established`** | `.eval-evidence/ledgerB1-full/` |
| `ledgerB2` | B | 关主动压缩（阈值 = 窗口） | 3 | — | — | `.eval-evidence/ledgerB2-full/` |

证据目录不入库（`.gitignore:9`），本文所有数字均从其中的 `runs.jsonl` 与 `sessions/*/events.jsonl` 读出。

**不可行项**：四臂的 `infeasible` 计数**都是 0**，`excludedInfeasible` 与 `excludedErrored` 也均为 0——没有任何一次运行需要按「拒绝但可解 / 不可行 / 基础设施失败」的口径从分母里排除。

**真正做不了的**（不是运行失败，是测不出来）：

- **批次 B 的处理效应**——自变量从未被触发：两臂的主动压缩计数都是 0。这是**仪器未成立**，不是「主动压缩无影响」。
- **任何比率型结论**——`n=3` 且解码未固定，预注册已把这一点写死（反 p-hacking 条款）。
- **长任务、大仓库、无公开检查的真实场景**——本装置不外推。

## 仪器与不变量

- **模型**：`deepseek/deepseek-v4-flash`，服务端回显 `model=deepseek-flash`。端点 `https://api.deepseek.com`，窗口按 PLAN 保守配置 1,000,000。
- **四臂的差异只有一个字段**（实现见 `scripts/eval-runner.ts` 的 `ledgerPolicy`）：

| 臂 | `inputTargetTokens` | `compactionBudgetTokens` | 该臂上「处理」是否出手 |
| --- | ---: | ---: | --- |
| `ledgerA1` | 1,000,000 | 1,000,000 | 都不出手（不裁） |
| `ledgerA2` | **22,791** | 1,000,000 | 裁剪出手 |
| `ledgerB1` | 65,536 | 未设 → 65,536 | 主动压缩在 52,428 处出手 |
| `ledgerB2` | 65,536 | **1,000,000** | 主动压缩不出手 |

- **A2 的目标是现算的**：A1 跑完 3 次之后，取 A1 每次运行 `context/projection` 里 `estimatedInputTokens` 的最大值、再跨重复取最大，乘 0.75 取整——即 `floor(0.75 × 30,389) = 22,791`，写死在[预注册](PLAN.md#预注册两批开跑前写死)里。**目标冻结之前未读任一臂的 `accepted`**：推导工具 `pnpm eval:ledger-target` 只读 `runs.jsonl` 里的层 A 处理量，不读 `report.json`、不打印 `accepted`。
- **单次 run 预算，按阶段各计一份**：32 请求 / 64 工具 / 300,000ms / 2,000,000 token。`ledger` 是 4 个阶段，每个阶段各新建 `RunState`、counters 归零，因此每次运行的上界是「4 × 这组值」。请求数 32 是**约束**（四臂获得相同工作量），2,000,000 token 是**兜底**。
- **整批上限**（运行器侧硬中止，按阶段独立计数）：每臂 384 请求 / 24,000,000 token。**是逐阶段预算的理论上界，不是按实测的预注册**；实测远低于此。
- **验收判据**（四臂同一套）：退出码 0 + stdout 恰好等于该 fixture 的验收标记 + 受保护文件零改动。终态一次性判定，不按阶段拆分。

## 判据分层：层 A 操纵检查，层 B 结局

两层的顺序**不可交换**：先看结局再看处理，等于允许用「无差异」把「没测到」说成「没有」。层 A 不成立时报**仪器未成立**，不进入层 B，也不得把层 A 的读数改写成结局结论。

**层 A 的量全部取自 `summarizeStage` 已记录的字段**（`maxEstimatedInputTokens`／`removedTaskIds`／`firstPrunedProjection`），压缩计数从 `context/summary-end` 按 `startSeq` 配对、按 `trigger` 拆开现算。判据不新增埋点。

### 批次 A：`ledgerA1` 对 `ledgerA2`

| 臂 | 逐次峰值估算输入 | 裁剪是否出手 | 被移除的任务组 |
| --- | --- | --- | --- |
| `ledgerA1` | 25,711 / 30,389 / 26,871 | **否**（三次运行全部 `removedTaskIds` 为空、`firstPrunedProjection` 为 `null`） | 无 |
| `ledgerA2` | 21,742 / 22,696 / 22,783 | **是**（三次运行都出现裁剪） | 每次都是第 0 阶段的任务组 |

**层 A 的两条判据都成立**：A2 的 `removedTaskIds` 每次都含第 1 阶段的 `taskId`（裁剪够到了载体）；两臂的处理量区间不重叠（A1 最低 25,711，A2 最高 22,783）。裁剪一旦出手，后续阶段的峰值随即塌下来（A2 末阶段 15,233／21,302／16,616 对 A1 的 25,711／30,389／26,871）。

**层 B**：A1 逐次 `accepted` 为 true／true／true，A2 为 true／false／true——**取到两个不同的值**，字面命中第 3 类。那次失败是一次真·任务失败，见「失败案例」一节。

### 批次 B：`ledgerB1` 对 `ledgerB2`

| 臂 | 逐次峰值估算输入 | 裁剪是否出手 | 主动压缩 `applied`（其中 `pressure`） |
| --- | --- | --- | --- |
| `ledgerB1` | 24,984 / 27,003 / 24,787 | 否 | 0（**0**） |
| `ledgerB2` | 30,359 / 33,189 / 44,252 | 否 | 0（0） |

**层 A 不成立，判定 `instrument-not-established`**：B1 的 `pressure` 计数为 0——**自变量从未被触发**。两臂在构造上等价（都不裁、都不压），因此两臂之间的一切差异都只是采样，不是处理效应。

**机制**：B1 的主动压缩在 `65,536 × 0.8 = 52,428.8` 处出手（`src/core/agent-loop-runtime.ts:111`，`compactionRatio` 缺省 0.8 见 `src/core/budget.ts:30`）。B1 三次运行的最大输入峰值是 27,003，够不着这条线。

**这条「够不着」的余量要如实说，它并不宽**：六次 B 批运行里，`ledgerB2` 的第三次从第 0 阶段起就取了另一支行为样本（峰值 33,289／37,439／40,271／44,252），摸到 44,252，到出手线只差 16%。所以「这台装置在当前尺寸下答不了 B 的问题」成立，但**它离答案的距离比只看 B1 时显得更近**。这不是处理效应——`ledgerB2` 与 `ledgerB1` 在压缩不触发的前提下行为完全等价。

## 失败案例

批次 A 里唯一一次 `accepted === false`（`ledgerA2` 第 2 次运行，`repeat=1`）是**真·任务失败，不是基础设施失败**：`status` 仍为 `completed`，退出码 1，`protectedFilesChanged` 为空。验收器 `test/fixtures/coding/ledger/verify.mjs:47` 的断言原文：

```
AssertionError [ERR_ASSERTION]: checksum does not follow the agreed reconciliation basis
0 !== 550679
```

终态的账目校验值算成了 0，即该约定要求的产物没有落成。

**这次读数不能支持什么**：它是三次重复里的**一次**，而来源指纹逐字写明 `temperature/seed 未发送、thinking 打开、重复独立采样`（四次开跑的 `provenance.sampling` 完全一致）。拿一次翻转去讲「裁剪导致失败」，正是反 p-hacking 条款要挡的东西。**只能记成「本批观测到一次失败」，不能记成「裁剪使失败变多」。**

## 结论边界

**可以写的（Harness 行为与仪器可用性）：**

- 这台装置有能力分辨「裁」与「不裁」：A2 每次运行都裁掉了第 0 阶段的任务组，两臂的处理量区间不重叠，结局也取到了两个不同的值。
- 裁剪的效果是**结构性**的：要它出手需要「存在已结束的旧任务」与「累计估算输入越过目标」两个条件同时满足。
- 预算与整批上限从未成为约束，usage 全部来自 provider。
- 四条臂的差异确实只来自 `ledgerPolicy` 的那一个字段——离线预演里 `ledgerB1` 与 `ledgerB2` 的输出只差「主动压缩」一行。

**不能写的（真实模型能力）：**

- 任何比率、任何提升、任何「哪条臂更好」的判断。
- 把批次 A 的 `ceiling-broken` 读成「裁剪有害」或「裁剪有益」——它只说装置分辨得出来。
- 把批次 B 的 `instrument-not-established` 读成「主动压缩没有价值」——那是自变量没被触发，不是处理无效。
- 把批次 A 那次失败外推成任何频率或趋势——`n=3`、一次翻转、解码未固定。
- 把「A2 的目标够得着、B1 的阈值够不着」读成两组装置可比——两个数字回答两个不同的问题。

**一句话**：本报告证明的是**这台装置能分辨上下文策略的差异，且其中一批的自变量在真实模型上确实被触发**；它不证明裁剪对任务结果的影响，也不证明主动压缩有没有价值——**后者连自变量都没触发**。要让 B 的问题可答，需要换一类上下文规模自然越过 52,428 的任务，那是新 fixture、新契约与一次新的付费授权，不是继续调 `ledger`。

## 证据位置与复现入口

- 原始证据（不入库）：`.eval-evidence/ledgerA1-full/`、`ledgerA2-full/`、`ledgerB1-full/`、`ledgerB2-full/`，各含 `runs.jsonl`、`report.json` 与 `sessions/`。
- 每条 run 的 `runs.jsonl` 一行含状态、counters、验收结论与逐阶段明细（含 `maxEstimatedInputTokens`／`removedTaskIds`／`firstPrunedProjection` 与 `compactions`）。
- **判定可离线重算**：`pnpm eval:ledger-verdict A` / `B` 读两臂的 `runs.jsonl` 现算四类结局；`pnpm eval:ledger-target` 从 A1 的证据现算裁剪目标。两者都不发请求、不花钱。
- 付费入口 `pnpm eval:screening --phase <臂名>` 每次调用都需要新的明确授权；证据目录每次运行只能用一次（`ensureWritable` 拒绝复用），这也是四臂各占一个目录的原因。
- 离线可复现的部分：`pnpm eval:offline`、`pnpm fixtures:check`、`pnpm test`。三者都不调用付费模型。
